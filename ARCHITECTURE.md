# Architecture

## Goal

Replace the core workflows of ManageEngine DataSecurity Plus:

1. **File Audit / FIM** — who touched what file, when, from where.
2. **Data Risk Assessment (DRA)** — where is sensitive data (PII/PCI/PHI-shaped content) sitting, and is it over-exposed.
3. **Ransomware / anomaly detection** — spot mass-encryption/mass-delete behavior fast, raise an alert, and let a human approve a response action.
4. **Disk/storage analysis** — track storage growth and usage per share/path over time.

## Design decisions

**All TypeScript for v0, not Go/Rust for the agent.** DSP's real agent needs to run as a low-footprint Windows service reading the NTFS USN journal, which argues for Go or Rust in production. This dev environment doesn't have a Go toolchain, and the priority right now is proving the end-to-end pipeline (event → rule → alert → dashboard) rather than agent footprint. The agent package is isolated behind a plain HTTP ingest contract specifically so it can be rewritten in Go/Rust later without touching the backend, classification worker, or dashboard — only `packages/agent` changes.

**A native agent (`native-agent/`, Go) now exists alongside `packages/agent`, not in place of it — a rewrite of local-path watching only, not the whole package.** SMB/M365/Google Drive stay on the TypeScript agent; this specifically replaces `SOURCE_TYPE=local`'s dependency on the Node.js/V8 runtime with a single static binary (~9MB, no CGO), which is the actual footprint win the design decision above named. Built with `fsnotify` (inotify on Linux, `ReadDirectoryChangesW` on Windows), **not the NTFS USN journal** the original ambition specified — that's a deliberate scope reduction, not a shortfall discovered later: USN journal parsing (resolving file reference numbers back to paths, journal ID/wraparound handling, getting `FSCTL_QUERY_USN_JOURNAL`/`FSCTL_READ_USN_JOURNAL` exactly right) is real systems-programming risk on a production file server's *boot volume*, and no Windows machine exists anywhere in this project to test any of it against a real NTFS volume. Shipping unverified low-level journal-reading code against that specific risk profile — where a mistake's blast radius is a production server's system volume, not a userspace watch failing — was judged not worth it. `fsnotify`'s Windows backend still delivers the actual goal (no Node runtime, one static binary) safely.

**Same wire contract, verified by construction, not by inspection.** `native-agent/internal/wire` hand-matches `packages/backend`'s Zod schemas (`ingest.ts`, `agents.ts`) field-for-field, and `internal/config`'s agent-key derivation reproduces `packages/agent/src/config.ts`'s formula exactly (`agent-<sha256(hostname:local:watchPath)[:24]>`) — pointing the Go agent at the same host and `WATCH_PATH` a TypeScript agent previously used re-registers under the *identical* `Agent.key` rather than minting a duplicate, so a deployment can switch agent implementations without losing history. Live-verified end to end against a real backend: register, create/modify/delete detection, storage snapshots, the full classification pipeline (a real alert from a real PII-shaped test file), and the quarantine approve→execute round trip (reusing `ARCHITECTURE.md`'s ransomware-burst quarantine's multi-path command shape and per-file-detail-in-the-message aggregation, same tradeoff, same reasoning). One real bug found and fixed during that verification, not designed around in advance: a naive "debounce based on which raw OS event arrived last" approach reported brand-new files as `modified` instead of `created`, because a single `echo x > f`-style write fires both a Create and a Write notification on Linux in quick succession — fixed by deciding created-vs-modified from whether the watcher had already seen that path before, at the moment the debounce timer fires, not from the raw event type (see `internal/watch/watch.go`'s `debounce`).

**Postgres only, no Kafka/Elasticsearch yet.** Event volume at pilot scale (a handful of watched paths) fits comfortably in a well-indexed Postgres table partitioned by day. Introducing a stream broker or search cluster before there's a concrete scale/query problem would be premature — revisit if/when: (a) ingest volume needs durable buffering across backend restarts, or (b) full-text/fuzzy search across audit history becomes a product requirement.

**Rules run inline in the backend, not a separate stream processor.** The ransomware/anomaly rule (event-rate-per-agent-per-minute) is cheap enough to evaluate synchronously on ingest. A dedicated stream-processing layer (Flink/ksqlDB-style) is overkill until rules get materially more complex (cross-path correlation, ML-based baselining).

**Classification is a separate worker, not inline on ingest.** Content scanning (reading file bytes, running pattern/format checks) is I/O- and CPU-heavier and shouldn't block the hot ingest path. It polls a `ClassificationJob` queue backed by Postgres (`pg-boss`-style `FOR UPDATE SKIP LOCKED`), which avoids standing up Redis/RabbitMQ for v0 while still being safe for multiple workers.

**Classification runs a regex pass and a local NER pass, not just one or the other.** `packages/classification/src/patterns.ts` (unchanged) catches structured data — SSN, Luhn-checked credit card, email, phone. `packages/classification/src/ner.ts` adds unstructured detection — person names, organizations, locations — via a local named-entity-recognition model (`@huggingface/transformers` running `Xenova/bert-base-NER`, CoNLL entity types PER/ORG/LOC; MISC is dropped as too broad to be a useful signal). **Local was a deliberate choice over calling a cloud LLM API**: a data-security product routing the content it's protecting through a third-party API to classify it would undermine its own purpose, and would be a real compliance problem for actual PII/PHI. "Local" means inference — the part that touches file content — never leaves the machine via ONNX Runtime/WASM. Model *weights* (~100MB, cached under `packages/classification/.cache/`, gitignored) download once from Hugging Face Hub on first run; that's a one-time setup step comparable to `docker pull`, not an ongoing data path, but worth being explicit about so "local model" isn't misread as "no internet, ever." The model loads once at worker startup (`preloadNerModel()`, before the poll loop begins) rather than per job, so a broken load fails loudly at boot instead of silently mid-job, and the first real classification job isn't stuck paying multi-second load latency. Matches below a confidence threshold (0.85) are dropped — BERT NER can misfire on short/lowercase tokens. **Known v1 tradeoff, not yet solved**: NER inference runs sequentially per job like the regex pass, and is meaningfully slower (seconds, not microseconds) — this will visibly reduce worker throughput under load; batching/concurrency is a natural follow-up once that's a real bottleneck rather than a hypothetical one.

**Automated response is a suggest-and-approve loop, not literal automation, and only does what the system can actually do.** Real DSP-style responses ("disable this share," "kill this process") assume the tool operates the file server — logikos-dsp's agent is a client that watches shares, it doesn't administer them, so those aren't implemented. v1 has two response action types: **webhook notification** (`packages/backend/src/responseActions/webhook.ts`, sending alert details to Telegram and/or a generic `RESPONSE_WEBHOOK_URL` — see "Telegram notifications") and **file quarantine** (local-path agents only, see below). Nothing fires automatically regardless of severity: HIGH/CRITICAL alerts get `ResponseAction` row(s) created in `PENDING` status (by `packages/backend/src/rules/ransomwareRate.ts` for CRITICAL ransomware-rate alerts — notification only, there's no single file to quarantine; by the classification worker for HIGH sensitive-data alerts — both notification and quarantine, independently), and nothing executes until an ADMIN calls `POST /response-actions/:id/approve`; `POST /response-actions/:id/reject` dismisses a suggestion as a false positive without executing anything. This is a firm product requirement, not a placeholder to relax later. `ResponseAction` is its own table (not columns bolted onto `Alert`) so the alert lifecycle (open/acknowledged/resolved) and the response lifecycle (pending/approved/rejected/executed/failed) stay separate concerns.

**File quarantine can't execute synchronously in the approve request, unlike webhook notification — only the agent has filesystem access to the watched directory.** Approving a `FILE_QUARANTINE` action sets it to `APPROVED` (a status that exists *only* for this reason — webhook notification skips straight to `EXECUTED`/`FAILED`), not a final state. The local-mode agent polls `GET /agent-commands?agentKey=...` (`packages/agent/src/quarantine.ts`, `packages/backend/src/routes/agentCommands.ts`) — the same "which file, which agent" data already lives on the linked `Alert` (`agentId`, `metadata.path`/`metadata.affectedPaths` — see below), so no new columns were needed on `ResponseAction` — moves the file(s) into a `.logikos-quarantine/` subfolder *inside* the watched root (no new permission surface, no new `QUARANTINE_DIR` config), and reports back via `POST /agent-commands/:id/complete`, which is what actually sets `EXECUTED`/`FAILED`. That subfolder is excluded from the chokidar watch (`watcher.ts`'s `ignored` option) so the move itself never produces a spurious `FileEvent`. Both endpoints are agent-facing (`Agent.key`, never `app.authenticate`) — same two-identity-system split as `ingest.ts`. Quarantine is suggested only for local-path agents — `supportsQuarantine()` in `packages/shared` (see "SMB quarantine" below for why SMB isn't included despite being a write-capable-in-principle share).

**Ransomware-burst quarantine: the same `FILE_QUARANTINE` mechanism as a single sensitive-data alert, generalized to a list of paths instead of one.** A `RANSOMWARE_RATE` alert has no single file to act on — it's an event-rate burst — but it does have a *set* of them: `checkRansomwareRate()` (`packages/backend/src/rules/ransomwareRate.ts`) queries every `created`/`modified` `FileEvent` in the trigger window, dedupes by path, caps at `MAX_QUARANTINE_PATHS` (200 — bounding metadata size and the reviewable command list, not a claim that files beyond the cap are safe), and stores it as `metadata.affectedPaths`. Rather than add a new response-action type or a per-path row, `GET /agent-commands` normalizes both shapes (`metadata.path` for a single sensitive-data file, `metadata.affectedPaths` for a burst) into the same `paths: string[]` command — one `QuarantineCommand`, one or many paths, one agent-side code path (`quarantine.ts`'s `pollOnce`) either way. The tradeoff this creates: approving is still one click for the whole burst, but `ResponseAction` has one `status`/`resultMessage`, not one per file — a 50-file burst that quarantines 47 and fails 3 reports `FAILED` with per-file detail folded into `resultMessage`'s text (`"quarantined 47/50 file(s); failed: ..."`), not as its own partial-success status. A known, deliberate simplification (approve-first is about a human deciding *whether* to act on a burst, not auditing every file individually), not an oversight — and same-shaped as `SENSITIVE_DATA_EXPOSED`'s single-file case when there's exactly one path, so no special-casing needed for the common case. Live-verified against a real local-mode agent (55-file burst, all 55 quarantined in one approve), not just unit-tested — same rigor bar as the SMB/local connectors, unlike M365/Google Drive.

**SMB quarantine was attempted, and reverted after live verification showed it doesn't actually work.** The obvious extension — `SmbSource` gains a `quarantine()` using `v9u-smb2`'s `mkdir`/`rename`, `supportsQuarantine()` includes `smb://` — was built, then tested against this project's own test Samba container (`docker-compose.smb-test.yml`) exactly the way the read connector itself was originally verified. It failed with `STATUS_ACCESS_DENIED`, and not because of a filesystem-permission mistake (the container's bind-mounted directory has normal read/write permissions for the share user). Reading `v9u-smb2`'s source found the real cause: every write-path request builder (`lib/messages/create.js`, used by `rename`'s fallback path; `lib/messages/create_folder.js`, used by `mkdir`) hardcodes `WRITE_DAC` into the SMB2 `CREATE` request's `DesiredAccess` — a right to modify an object's *ACL*, not just its content. A properly-secured Samba server correctly denies that to a normal, non-admin share user, so the create/open underlying every write operation fails outright, independent of whether the account has real file read/write permissions. Confirmed directly: pre-creating the quarantine folder out-of-band and retrying just the `rename` call still failed the same way. Read operations (`readdir`/`readFile`) are unaffected — they go through a different request builder (`lib/messages/open.js`) that doesn't request `WRITE_DAC` — which is exactly why the existing read-only connector has always worked. There's no clean fix available without patching the dependency (forking it, or monkey-patching its internal message classes, both real added maintenance surface for a v1 feature); reverted rather than ship something that fails in exactly the deployment shape (a properly-secured file server) this product exists to protect. `supportsQuarantine()` continues to exclude any `scheme://` watchedRoot.

**The "suggest a response action" step is duplicated in the two places that create alerts, not centralized.** Alerts are created from two different processes with two different DB clients — the backend's ransomware-rate rule (Prisma) and the classification worker (raw `pg`, see below). Rather than force a shared abstraction across that process boundary, or use a Postgres trigger (which would make the suggestion policy invisible from reading either codebase), each call site gets its own small "if severity is HIGH/CRITICAL, also insert a PENDING `ResponseAction`" step, right next to where it creates the `Alert`. Consistent with this project's general preference for explicit over magic (the seed script instead of auto-created admin, explicit env vars throughout) — a few duplicated lines that are easy to find beat one clever mechanism that isn't visible from either call site.

**Storage analysis piggybacks on the agent.** Rather than a separate crawler, the agent periodically walks its watched root and reports aggregate size/file-count snapshots — same transport, same auth, no new component.

**Renames are detected by pairing, not reported by the protocol.** A scan compares two lists of paths, so renaming a file looks like a delete plus a create — which is how it appeared in the dashboard until a rename in testing made it obvious. A rename leaves contents untouched, so both halves share an exact size and mtime: `diffSnapshots` pairs a disappeared path with an appeared one on that key and emits one `renamed` event carrying `previousPath`. Only unambiguous pairs count — two files gone and two appeared with the same size and timestamp (several empty files made in the same second) stay as deletes and creates rather than inventing a pairing — and a copy is still a create, since the original is still there. Renamed paths join created/modified ones in a ransomware burst's quarantine list, because mass-renaming is what ransomware does to files it has just encrypted. **Copying is two different questions, and only one is visible to a scan.** Copying a file *into* or *within* a share creates a file, and a copy keeps the original's size and last-write time — so a new path matching a file that is *still present* is a copy of it (`pairCopies`; the difference from a rename is precisely that the original survives). Reported as its own `COPIED` event carrying the source in `previousPath` — but only when exactly one identical file is still there, since every empty file matches every other one. That alone proved too strict against a real share: three files pasted from one folder to another came through as creates, because empty files are ambiguous and identical copies of the same zip were sitting around. The stronger signal is the timestamp. Copying preserves the last-write time, so a file whose contents predate the *previous scan* cannot have been written in the share since — it was pasted in, whatever its source. That also catches a paste from outside the share, where no source exists to name, and those arrive as `COPIED` with no `previousPath`. A file genuinely written since the last scan has a newer timestamp and stays a create. Naming the source among several identical files then uses the one thing a copy or a move keeps: its filename. With two 22-byte zips on the share, "which one was this copied from" is unanswerable by size and timestamp, but exactly one of them is called `create file.zip` like the new file — and when no candidate's name matches either, nothing is named, because a wrong source is worse than none. The same rule pairs a move between folders with the file that left it. Where even that fails — a real share had `create file.zip` in three folders with identical size, timestamp *and* name, so nothing in the filesystem says which one was copied — the audit log settles it: copying reads the source before writing the target, so a read of a file with the same name, just before the copy, names it (`inferCopySourceFromReads`). That needs read recording on for the server; without it copies simply carry no source, which is the honest answer rather than picking one of three at random. The same read also rescues the case the scan can't classify at all: create a file and copy it within one interval and *neither* existed at the previous scan, so there's no original to match and both arrive as creates — a read of the same filename moments earlier turns the second one into a copy. Only the creator's own read counts; someone else opening a same-named file is a coincidence, not a source. Copying a file *out* of a share, though — the exfiltration case — changes nothing on the share: no scan can ever see it. Its only trace is a read in the Windows audit log, which is why read recording exists as a per-server opt-in (reads are most of a busy share's audit volume, so they are dropped in the agent unless asked for) and why `BULK_FILE_READ` alerts on one account reading more than 50 *distinct* files in five minutes — distinct, because Windows logs a document re-read all morning many times over and that isn't an exfiltration. The **File Access** view shows that trail directly, since it is not a change and doesn't belong in File Events.

**A rename between two scans is reconstructed from the audit trail instead.** Pairing only works when the old name was in the previous snapshot; rename a file within one scan interval of creating it and the old name was never seen, so the share simply gains a file and the scan reports a create — with no author, because Windows logs a rename as a *delete of the old name* and nothing against the new one. That delete is the tell: a delete record with no deletion of its own, beside a create with no write of its own, is that rename (`inferRenameFromAudit`, applied from both ingest paths). Only when exactly one delete fits — with two candidates there's no way to know which file became which, and an invented author is worse than a blank one, so an ordinary create-and-delete in the same minute is left alone. This is inference from two independent signals, not something the protocol reported; a real-time Windows agent would see the rename directly.

**Local-path watching still reports a rename as delete + create**: chokidar doesn't report renames, and once a file is gone its size and mtime can't be read to pair it with anything.

**Storage sources are pluggable behind a `Source` interface, each free to use its own detection strategy.** `packages/agent/src/sources/types.ts` defines `Source` (`describe()`, `listTree()`, `readSample()`). Local paths (`packages/agent/src/watcher.ts`) use `chokidar` for real-time OS filesystem events, unchanged since v0. SMB/network shares (`packages/agent/src/sources/smb.ts`) instead use **periodic snapshot diffing** (`packages/agent/src/snapshotDiff.ts`): walk the share on an interval, diff against the previous walk's `{size, mtime}` map, synthesize created/modified/deleted events. This was a deliberate choice over mounting the share locally and reusing chokidar — CIFS/NFS client mounts don't reliably propagate inotify events for remote-side changes, so a "real-time" mount-based watcher can silently miss changes. The tradeoff is detection latency bounded by the scan interval (`SMB_SCAN_INTERVAL_MS`, default 30s) instead of true real-time, and — same limitation chokidar already has for local paths — no reliable rename or permission-change detection (a move shows up as delete+create). One walk serves both FIM events and the storage snapshot for SMB sources, since the tree walk already has full size/count data; local mode still does these separately (chokidar has no "list everything" step to piggyback on).

This required **no backend or dashboard changes** — `Agent.watchedRoot`, `FileEvent.path`, and `StorageSnapshot.rootPath` were already unconstrained strings, so an SMB agent just registers with `watchedRoot: "smb://host/share/sub"` and everything downstream works unchanged. Confirms the v0 bet on isolating the agent behind a plain HTTP contract.

**SMB client: `v9u-smb2`, not the more well-known `@marsaud/smb2` it forks — verified the hard way.** Both are pure-JS SMB2/3 clients (no OS-level `mount -t cifs`, no root/CAP_SYS_ADMIN needed — works from a container), and both self-describe as "experimental." `@marsaud/smb2` was tried first and rejected: it bundles the `ntlm` package, which only ever speaks NTLMv1 (confirmed by reading its source — no HMAC-MD5/NTLMv2 code at all) and reliably failed `STATUS_LOGON_FAILURE` against this project's test Samba container even with NTLMv1 explicitly permitted server-side. `v9u-smb2` swaps that dependency for `ntlm2`, which implements real NTLMv2, and connects successfully. Both libraries still hash the legacy LM response via DES-ECB and the NT hash via MD4 — algorithms OpenSSL 3's default provider disables — so **the agent process requires `NODE_OPTIONS=--openssl-legacy-provider` whenever `SOURCE_TYPE=smb`** (see README). Separately, the shipped `index.d.ts` doesn't resolve cleanly as a default export under this project's `moduleResolution: NodeNext`, and omits `size` from stat results even though the underlying implementation always sets it (verified by reading `lib/tools/stats.js`). `sources/smb.ts` works around both by loading the package via `createRequire` and declaring only the surface it actually uses, checked against the real implementation — rather than fighting the package's types. If `v9u-smb2` itself proves unreliable in practice, the next fallback is shelling out to the `smbclient` CLI, not pursued since NTLMv2 auth is now working.

**Microsoft 365 (OneDrive/SharePoint) connector: same `Source`/snapshot-diff machinery as SMB, zero changes to that shared code.** `packages/agent/src/sources/m365.ts` implements `describe()`/`listTree()`/`readSample()` like `sources/smb.ts` does — the only new code is a third `Source`, everything downstream (diffing, event batching, storage snapshots) is already-proven infrastructure. Auth is the OAuth 2.0 **client credentials grant** (app-only, no user sign-in — an Azure AD app registration with `Files.Read.All`/`Sites.Read.All` **Application** permissions and admin consent, the standard "daemon app" shape), implemented with plain `fetch` rather than `@azure/msal-node` or the Graph SDK — token acquisition is one documented `POST`, not worth a new dependency. One configured `M365_DRIVE_ID` (+ optional `M365_SUBPATH`) per agent, matching the SMB connector's "one configured share" scope — no org-wide auto-discovery of every user's OneDrive or every SharePoint site. Uses Graph's plain paginated `children` listing on a scan interval (`M365_SCAN_INTERVAL_MS`, default 60s — more conservative than SMB's 30s, since this hits a rate-limited cloud API), not Graph's `/delta` incremental-changes API — delta queries would mean new state (delta tokens) and a genuinely different code path, and given this connector can't be tested against a real tenant right now (see below), minimizing new mechanism surface mattered more than the efficiency win.

**This connector has not been verified against a real Microsoft 365 tenant** — unlike every other connector in this project (SMB was checked against a real test Samba container; the local watcher, obviously, against a real filesystem), no Azure AD credentials were available while building it. Every endpoint, request/response shape, and auth flow detail above is grounded in Microsoft's current Graph API documentation (fetched and read directly while designing this, not recalled from training data), and the pure response-parsing logic (`parseChildrenPage` in `sources/m365.ts`) is unit-tested against fixture JSON copied verbatim from Microsoft's own documented example responses — but the actual network calls, real permission/consent behavior, and error responses are unverified. Treat the first real run against a live tenant as the actual verification step, and watch its logs closely.

**Google Drive connector: same `Source`/snapshot-diff machinery as SMB and M365, zero changes to that shared code.** `packages/agent/src/sources/googledrive.ts` is the fourth `Source`. Auth is a Google service-account **JWT Bearer flow** (RFC 7523) — the service account's private key signs a short-lived assertion, exchanged at `oauth2.googleapis.com/token` for an access token scoped to `drive.readonly` — implemented with `node:crypto`'s `createSign` and plain `fetch`, not `googleapis`/`google-auth-library`, same "one documented POST, not worth a new dependency" call as M365's client-credentials grant. Access is granted per-folder by sharing that folder with the service account's email, like sharing with any other Google user — deliberately not Workspace domain-wide delegation (which needs a Workspace *admin*, not just the folder's owner, and doesn't exist at all for personal, non-Workspace Google accounts) — so a single `GDRIVE_FOLDER_ID` covers both a personal Drive and a Workspace one with the same auth flow, no `corpora`/org-wide branching. One real Drive-specific wrinkle SMB and M365 don't have: native Google Docs/Sheets/Slides (`mimeType` prefixed `application/vnd.google-apps.`) have no binary representation — `alt=media` (the same download endpoint used for every other file) 403s on them — so `parseFilesPage` skips them from `listTree()` entirely rather than teaching `readSample()` to call `files.export` with a per-type target format for a case judged not to be where structured PII actually lives.

**Unlike M365, this was built from recalled knowledge of Google's Drive API v3 and OAuth2 service-account documentation, not fetched and re-read live during design** — worth being explicit about, since the M365 section above specifically calls out having done the latter. Every endpoint, field name (including that `size` is a numeric *string* on the Drive `File` resource, not a number, confirmed by memory of the resource reference rather than a fresh read), and auth-flow detail is believed accurate but carries the usual risk of a trained-knowledge recall being subtly stale or wrong in a way a live doc fetch would have caught. Same bottom line as M365 regardless: **not verified against a real Google account** (no service-account credentials were available), the pure response-parsing logic (`parseFilesPage`) is unit-tested against a fixture shaped to match the documented `Files.list` response, and the first real run against a live account is the actual verification step.

**The classification worker's "is this agent local (write-capable)" check generalizes from an `smb://`-specific prefix check to "watchedRoot contains no URI scheme."** `packages/classification/src/watchedRoot.ts`'s `isLocalWatchedRoot()` — `!watchedRoot.includes("://")` — decides whether a `HIGH` sensitive-data alert also gets a `FILE_QUARANTINE` suggestion alongside the webhook notification. SMB, M365, and Google Drive watchedRoots all carry a `scheme://` prefix and are all read-only in v1, so this one check now correctly excludes all three (and any future URI-based connector) without an ever-growing prefix allow-list — confirmed when the Google Drive connector landed with zero changes needed here.

## Data flow

```
 watched filesystem
        |
        v
   [agent]  --(FileEvent)-->  POST /ingest/events  --> [backend] --> Postgres (file_event)
        |                                                  |
        |--(StorageSnapshot, periodic)-->  POST /ingest/storage        |-- rate rule --> alert (Postgres)
                                                                        |
                                                        [classification worker] <-- polls classification_job
                                                                        |
                                                                        v
                                                        classification_match (+ alert if sensitive)

                                        [dashboard] <--REST--> [backend]  (events, alerts, storage trends, matches)
```

## Core entities (Prisma schema, `packages/backend/prisma/schema.prisma`)

- `Agent` — a registered watcher (host + its own env-configured watched root).
- `Source` — one watched root: an agent's own (created at registration) or a dashboard-managed SMB share. Events, snapshots and alerts hang off it. See "Dashboard-managed file servers".
- `FileServer` — an SMB server configured in the dashboard (host, account, encrypted password); its shares are `Source` rows.
- `ConnectionTest`, `AuditLog` — a "test connection" request for an agent to run, and who changed monitoring configuration.
- `FileEvent` — one filesystem event (create/modify/delete/rename/permission_change), from an agent, on a source.
- `StorageSnapshot` — periodic size/file-count rollup for a source.
- `ClassificationJob` — queued "scan this file" work item, created on file create/modify events.
- `ClassificationMatch` — a sensitivity-pattern hit (type: SSN/credit-card/email/etc, with a redacted sample) for a file.
- `Alert` — a raised alert (ransomware-rate, sensitive-data-exposed, ...), with severity and status.
- `ResponseAction` — a suggested response to an alert (currently only `WEBHOOK_NOTIFICATION`), pending until an ADMIN approves or rejects it.
- `User` — a dashboard login (`email`, `passwordHash`, `role`). Unrelated to `Agent`, see below.

## Auth/RBAC

**Two identity systems, deliberately kept separate.** Agents authenticate as *machines* (`POST /agents/register`, `/ingest/*`, `/agent-commands*` — see "Agent authentication" below for how, which came later). `User` + a cookie-based JWT authenticates *people* using the dashboard, gating every other endpoint (`/events`, `/alerts`, `/storage`, `/classification-*`, `/agents` GET, `/users`). Mixing these would mean either forcing unattended agent processes to hold a user session (no such user exists) or weakening the dashboard's auth to match agents' simple shared-secret model — neither is right, so the two stay on completely separate code paths. In `packages/backend/src/app.ts`, agent-facing routes are registered with a comment marking them as never gated by user auth; dashboard-facing route files each self-gate via `app.addHook("onRequest", app.authenticate)`.

**Login is rate-limited two ways, because they stop different attacks.** The dashboard is on the public internet and previously accepted unlimited password guesses. A per-account lockout (5 consecutive failures, then 1/5/15/30-minute backoff, capped — never a permanent lock an outsider could inflict on an admin) stops guessing one account's password. It does nothing about one client trying one common password against many usernames, since no single account's counter moves — so failures are also counted per IP (20 in 15 minutes blocks that address for 15). Both live in Postgres (`User.failedLoginCount`/`lockedUntil`, `LoginAttempt`) rather than in memory: the limit shouldn't reset because a container restarted, and the attempt log is the evidence of what happened.

**Every failure answers the same thing**, whether the account doesn't exist, is inactive, has the wrong password, or is locked — otherwise the login form becomes a way to enumerate accounts and to confirm which ones have been locked. The locked check runs before the password comparison so a locked account can't be identified by response timing either. Locking an account raises a `LOGIN_ATTACK` alert (approve-first notification, like every other alert), once per lock rather than per attempt.

**Cookie-based JWT, not a session table.** Consistent with the "Postgres only, no extra infra" stance below: a signed JWT in an httpOnly cookie (`@fastify/jwt` + `@fastify/cookie`) needs no session store, while still being safe against XSS token theft (unlike JWT-in-localStorage). No refresh-token flow in v1 — a user just logs in again after the token expires; revisit if session lifetime becomes a real complaint.

**Two roles: `ADMIN` and `VIEWER`.** ADMIN can do everything, including managing users and acknowledging/resolving alerts (`PATCH /alerts/:id` requires it); VIEWER is read-only. A finer-grained role (e.g. can-acknowledge-but-not-manage-users) is a natural v2 addition once there's a real need for it.

**`@fastify/jwt`/`@fastify/cookie` are pinned to their last Fastify-4-compatible majors** (`8.0.1` / `9.4.0`) — their current majors (10.x / 11.x) require Fastify 5, which this project isn't on. Bumping Fastify itself would be the right way to pick up newer versions, not a piecemeal plugin upgrade.

**Bootstrap admin via a seed script, not auto-creation.** `packages/backend/prisma/seed.ts` creates one `ADMIN` from `ADMIN_EMAIL`/`ADMIN_PASSWORD` env vars if no `User` rows exist yet (`pnpm db:seed`) — explicit and scriptable, rather than a magic first-run behavior that's easy to trigger by accident.

## Agent authentication

**Until this, `Agent.key` was the only thing an agent presented, and it isn't a secret.** It's `agent-<sha256(hostname:source)[:24]>` — derivable by anyone who knows a hostname and a watch path — and `/agents/register` accepted any key with no credential at all. So anyone who could reach the backend could register an agent and inject fabricated file events, which drive fabricated `RANSOMWARE_RATE` alerts and quarantine suggestions. The gateway's 403 on those paths (see "Deployment behind a shared reverse proxy") was a stopgap, and until `PUBLISH_ADDR` it was bypassable from the LAN.

**Two credentials, both as `Authorization: Bearer`.** `AGENT_ENROLL_TOKEN` is a deployment-wide secret that only `/agents/register` accepts. Registration answers with a per-agent `agentSecret`, which every other agent route checks against the key it names. Only `sha256(agentSecret)` is stored (`Agent.secretHash`) — not bcrypt, because it's 32 random bytes rather than a human-chosen password, so a slow hash buys nothing. Unknown key and wrong secret both return 401, so the endpoints don't reveal which keys exist. An ingest batch must carry a single `agentKey`: the old per-event key resolution would otherwise let one agent's secret write as another.

**The secret rotates on every registration, and agents never persist it.** The alternative — issue once, store it on the agent — needs a writable state file in every agent container and a recovery story for losing it. Instead an agent registers at startup and, on any 401, re-registers once and retries (throttled to one attempt per 5s, concurrent 401s sharing one registration: `agentSession.ts` in TypeScript, the `regMu` path in the Go `client`). That one rule covers three situations: a restart, a database restore from a backup (which used to leave a running agent ingesting against a key the restored database didn't have — the reason `restore.sh live` restarts the agent), and the Go agent taking over a TypeScript agent's key, which is designed to work (see the native agent note) and now simply rotates the secret out from under the old process. The cost: whoever holds the enroll token can take over any agent's key. That's accepted because the enroll token is already the credential that can create agents; it's an operator secret, not something handed to each agent host separately.

**Revocation is an `ADMIN` action on the Agents page** (`POST /agents/:id/revoke` / `restore`). Revoking sets `revokedAt` and clears `secretHash`: the agent's next request gets 403 — which agents deliberately do *not* retry — and re-registration is refused even with the enroll token. Restoring only lifts the block; the agent's next request 401s, it re-registers, and it's back without a restart (verified end to end against both agents). Events an agent sends while revoked are dropped, not queued.

**This deployment sits behind Cloudflare, and that invalidated two controls until `real_ip` was configured.** `dsp.logikos.dev` resolves to Cloudflare edge addresses, so every request reached nginx from the edge rather than from the caller. Two consequences, both measured rather than assumed. First, the enrollment rate limit below did nothing: Cloudflare spreads traffic across many egress addresses, so ten rapid registrations keyed on `$binary_remote_addr` looked like ten separate clients and drew zero rejections. Second, and worse, the backend believed whatever client IP it was told — `$proxy_add_x_forwarded_for` appends the edge address to the *caller's* `X-Forwarded-For`, and `trustProxy` takes the leftmost value, so a request carrying `X-Forwarded-For: 203.0.113.99` was recorded in `LoginAttempt` under that address. That defeated the per-IP half of the login throttle (per-account lockout still held) and forged the request log, which is the only record of who approved a response action. The fix in `deploy/dsp.conf` is `set_real_ip_from` for Cloudflare's published ranges plus `real_ip_header CF-Connecting-IP`, and `proxy_set_header X-Forwarded-For $remote_addr` — overwrite, never append — so the backend receives exactly one value it can trust. It is scoped to this server block deliberately: asset, chms and school share the proxy and the same exposure, but they are separate projects. The note in "Deployment behind a shared reverse proxy" that `trustProxy` is safe only while the backend is reachable solely via nginx was true and quietly stopped holding the moment a CDN was put in front of it.

**The Go agent installs itself as a Windows service, because `sc.exe create` on a console program doesn't work.** Windows expects a service process to connect back to the SCM and report status within ~30 seconds; one that doesn't is killed with "the service did not respond in a timely fashion" (error 1053) — it looks installed and never runs. So the binary implements `svc.Handler` (`cmd/agent/service_windows.go`), detects being launched by the SCM with `svc.IsWindowsService`, and carries its own `install`/`uninstall`/`start`/`stop`/`status` subcommands; `agent install` also *performs* the install — it copies itself into Program Files, writes `agent.json` (ACL'd to Administrators and SYSTEM via `icacls`, by SID so it works on non-English Windows) and drops the CA, so deploying a machine is one command with no other files. The Cloudflare Origin CA is embedded with `go:embed` for the same reason: needing a `.pem` beside the binary is the difference between a one-command rollout and a two-step one, and at fifty machines that is the difference that matters. A PowerShell installer was written first and deleted after it broke on a real machine three ways at once — execution policy, the mark-of-the-web on a copied file, and Windows PowerShell 5.1 reading a UTF-8 script as ANSI, which turned an em dash into a parse error. A single executable has none of those failure modes, which is the whole argument for putting this in the binary. The agent work itself moved to `runAgent(cfg, stop)` in `run.go` so the console path, the service path and the container run identical code, differing only in how they're asked to stop. Choices worth keeping: LocalSystem (watching another user's profile needs more than that user's rights), automatic start with restart-on-failure at 30/60/120s (an agent nobody knows has stopped is worse than no agent — the dashboard simply shows no copies), a log file next to the executable plus event-log entries for start/stop/configuration errors (a service has no console), and validating the config *before* creating the service, while a console is still there to read the error. A GUI wizard was not built: NSIS can cross-build one from Linux but isn't installed on this host, and a flag-driven executable is what a deployment tool can actually drive unattended anyway.

**Removable media is watched while it's plugged in, and identified by device rather than letter.** Where USB storage is blocked for most people and permitted for a few, a copy onto it is the event worth waking someone up for — and it is entirely invisible to the file server, which only ever learns its file was read. `cmd/agent/watchset.go` keeps one watcher per root and lets roots come and go; a poll every three seconds (`GetLogicalDrives` + `GetDriveType`) adds a watch when a stick appears and drops it when it goes. Polling rather than device notifications because `WM_DEVICECHANGE` needs a window and a message loop, which a service doesn't have. One race is accepted and documented: a file copied within the poll interval of the drive appearing is missed, because the watch isn't there yet. Each volume is described once at mount (`GetVolumeInformation`) and every event from it carries the label and serial, because `E:` is reused by whatever is plugged in next and "which stick was it" is the question actually asked afterwards — the wire, Prisma, the Zod schema and the Go `wire` package all gained `removable`/`volumeLabel`/`volumeSerial` together, as that contract requires. `rules/copyToRemovable.ts` then raises one alert per device per five-minute burst (copying a folder is one action by a person), HIGH when the files trace back to a monitored share via `previousSourceId` and MEDIUM otherwise, since someone's own file on their own stick is worth recording but isn't an incident. Quarantine is deliberately not offered as a response: the copy that matters is on a device we don't control, and deleting the local original would destroy evidence without recovering anything.

**Watching a whole machine needed exclusions before it needed anything else.** An agent can now watch several roots — `watchPaths`, or `watchAllFixedDrives` which enumerates `DRIVE_FIXED` volumes at startup (`internal/drives`) so a machine that gains a disk needs no revisiting — with one `watch.Watcher` per root, since the roots are disjoint and a volume that can't be watched must not stop the others. The load-bearing part is `internal/watch/exclude.go`: Windows produces vastly more activity in its own directories than users ever do, and unfiltered that doesn't merely add noise, it buries the events that matter and makes the File Events view unreadable — the failure mode that makes people stop looking at a monitoring product. Excluded directories are skipped during the walk rather than watched and filtered afterwards (on a system drive that is hundreds of watches instead of tens of thousands, each costing a handle), and the same check runs at event time and inside the walk of a newly created directory — a test caught the last of those, where `MkdirAll` of a chain fires one Create event that was walking straight past the exclusion list. Matching is deliberately three simple shapes (tree prefix, bare segment name, `**/` segment sequence) because an unpredictable rule is worse than one that occasionally misses. Identity is the other subtlety: one root keeps the historical `sha256(hostname:local:path)` key so existing installs carry their history over, but two or more derive from the machine alone — otherwise adding a disk, or later plugging in a USB stick, would silently mint a new agent and orphan everything that machine had reported.

**A workstation agent is configured by a file, and reaches the backend by name over a LAN address.** Environment variables are how compose configures the bundled agent and they still work, but a Windows service runs as LocalSystem with no shell profile, and an installer that has to edit machine-wide environment variables and get a service to notice is a support problem — so `native-agent` reads an `agent.json` next to its executable (`internal/config/file.go`), with the environment overriding it so one setting can be changed for a single debugging run. `Resolve` is pure — file plus a `getenv` function in, config or error out — leaving `Load` as the thin layer that touches disk and exits, the same split `packages/agent/src/config.ts` keeps. Two settings exist only for this deployment shape. `connectIp` dials a chosen address while TLS still verifies `serverUrl`'s hostname, because the site is behind a CDN and resolving the name sends every file event from a workstation out to the internet and back to a server on the same LAN; an IP in the URL cannot replace it, since origin certificates carry DNS names and nginx routes by `server_name` (a bare IP lands on whichever vhost is first — measured: a 404 from asset's). `caCertFile` appends a private CA to the system pool, needed because the origin certificate here is issued by Cloudflare's Origin CA, which no Windows machine trusts. Trust is only added, never relaxed: there is deliberately no skip-verification option, and a test asserts the connection still fails without the CA. Verified end to end on Linux against the production backend over the LAN path — registered, snapshotted, and reported a create and a modify — then the test agent's rows were deleted.

**Remote agents: the gateway's 403s are gone, and registration is rate limited instead.** Watching where a file was copied *to* needs an agent on the receiving workstation (see the cross-source copy note), and that agent reaches the backend over the internet-facing vhost rather than the compose network — so the stopgap 403s on `/api/ingest/*`, `/api/agent-commands*` and `/api/agents/register` had to go. The first two are no longer a real exposure: they require a per-agent secret the backend rotates, which is exactly what this section built. Registration is different, because `AGENT_ENROLL_TOKEN` is one value shared by the whole deployment and an attacker reaching that endpoint gets unlimited guesses at it. `deploy/dsp.conf` therefore rate limits `= /api/agents/register` to 6r/m per IP with a burst of 3 (`limit_req_zone dsp_register`, declared at the top of that same file — `conf.d/*.conf` is included inside the `http` block, so the vhost file's top level is `http` context and the gateway's shared `nginx.conf` stays untouched, which keeps this change unable to affect the other three projects), answering 429 rather than 403 so a throttled agent logs something true. Six guesses a minute against 32 random bytes is not an attack, and a legitimate agent registers at startup and after a 401 — orders of magnitude below the limit. The residual risk is unchanged and accepted: the enroll token lives in plaintext on every machine running an agent, and whoever holds it can take over any agent's key. That is tolerable for a handful of servers and becomes the thing to fix — per-machine enrollment tokens issued from the dashboard — before this is deployed across many user workstations.

**Existing `Agent` rows have no `secretHash` after the migration**, so every agent must restart onto the new build (which registers with the token) — an old agent build gets 401 on everything. Agents and backend have to be upgraded together.

**The gateway blocks on the agent paths stay.** The bundled agent still reaches the backend over the compose network and doesn't need the edge. Removing them to allow agents on other hosts is now reasonable, but is its own decision: it exposes `/agents/register` to online guessing of the enroll token (256 bits if generated as documented, with no rate limit in front of it), and it would be the first time agent traffic crosses the internet.

## Dashboard

**Prompted by a real comparison against ManageEngine DataSecurity Plus, not a generic redesign.** Asked to compare the two UIs; the comparison itself is from general/trained knowledge of ManageEngine's product design patterns, not a live hands-on session with the real product — worth re-verifying against actual screenshots if this matters later. It surfaced four concrete gaps, addressed in the order found:

**1. No summary/overview — went straight into raw tables.** `packages/backend/src/routes/overview.ts` (`GET /overview`) aggregates in Postgres — open-alert counts by severity, a 14-day trend, the latest storage snapshot *per agent* summed (not every snapshot ever taken — Prisma has no "latest row per group" query, so this is two queries, `groupBy` for the latest `(agentId, takenAt)` pairs then `findMany` for those specific rows, rather than reaching for raw SQL in an otherwise Prisma-only package), and classification matches grouped by pattern type — rather than the client pulling full row sets from four existing endpoints and aggregating in the browser. `OverviewView.tsx` is the new default landing tab.

**2. Chart colors were validated against this app's actual surface, not eyeballed or inherited from a skill's defaults.** This dashboard is dark-only (no light mode, no toggle) — `scripts/validate_palette.js` (the project's dataviz skill) was run against the real chart background (`#0f1115`), not the skill's own default dark surface (`#1a1a19`), a different and darker background. All checks passed; status-color contrast came out better than the skill's own reference numbers since the real surface is darker. Any new chart should re-run the validator against `#0f1115`, not assume the skill's defaults apply.

**3. No filtering, sorting, or export — everything was a flat `limit=100` table.** Added to all four table views client-side (`packages/dashboard/src/tableControls.tsx`, `csv.ts`): search, dropdown filters, sortable column headers, CSV export. Deliberately client-side, no backend changes — every view already fetches its full working set in one call, and sorting/filtering that array in the browser is simpler than adding sort/filter params to four routes for data volumes this small; revisit if a view's row count grows past what's comfortable to ship in one response. **The generic sort implementation's first version did plain string comparison for every column**, which sorts `Alert.severity` alphabetically (CRITICAL, HIGH, LOW, MEDIUM) instead of by actual rank (LOW→CRITICAL) — caught only by clicking the header and reading the row order, not by review, since CRITICAL landing first looks plausible at a glance. Fixed with an optional per-field rank-map on `useSort` for ordinal columns (severity, status) — same "ordinal fields need their real order, not alphabetical" principle the dataviz skill applies to chart color, generalized to table sorting.

**4. Flat top-tab nav instead of DataSecurity Plus's module-grouped sidebar.** `App.tsx`'s `NAV_GROUPS` groups views under labels (File Audit, Data Risk Assessment, Disk Analysis, Administration) rather than a flat tab row — but deliberately **not** a literal 1:1 mapping onto DataSecurity Plus's exact module names: this product's Alerts view covers both ransomware-rate and sensitive-data alerts together, not split into a separate "Ransomware Protection" module the way DataSecurity Plus's actual taxonomy does, so the grouping reflects what logikos-dsp actually has rather than forcing a naming match it can't back up.

**5. No compliance-mapped views — added as a discovery lens, explicitly not a compliance audit.** `ComplianceView.tsx` groups existing classification matches by regulatory scope, but only into two groups, and says up front what it isn't. PCI-DSS's scope (payment card data) is well-defined by pattern type alone; GDPR vs. CCPA vs. HIPAA mostly turn on *who* the data subject is and *what sector* you're in, not which of SSN/email/phone/name was matched — presenting those as cleanly separable by pattern type would be false precision this view doesn't manufacture. A visible banner states plainly that real compliance also needs retention-policy enforcement, access-control review, and breach-notification procedures, none of which this product implements. This is a deliberate scope boundary, not a placeholder to relax later — expanding it into per-regulation pass/fail status would be a real claim about compliance posture that nothing in this product currently backs up.

**6. Responsive: usable on a phone and a tablet, not just "doesn't break".** Checked at 390px, 768px and 1280px against seeded data with realistic long paths, measuring horizontal overflow (`scrollWidth - innerWidth`) rather than eyeballing. Below 900px the sidebar becomes an off-canvas drawer behind a menu button (closes on selection, backdrop tap, and Escape; the top bar now names the current page at every width). Below 900px, `.data-table` rows also stack into labelled cards, driven by a `data-label` on each cell and pure CSS — no second mobile component tree to keep in sync. The breakpoint for cards is the drawer's, not a phone-only one, because the first attempt used horizontal table scrolling on tablets and that hid the Response column — exactly where the Approve/Reject buttons are. The cost of cards is that header-click sorting isn't available below 900px; each view already defaults to newest-first. Two things only showed up in screenshots: a cell with several child elements (the alert's response actions) lays each child into its own grid cell unless wrapped in one container, and a flex `<span>` badge stretches the full card width unless told not to. Inputs are 16px on phones so iOS doesn't zoom into them, and the overview's trend chart uses pointer events so its tooltip works on touch.

## Testing

Every feature up to this point was verified by hand — live processes, curl scripts, real Postgres, a real Samba container, a real webhook listener. That caught real bugs (an NTLMv1-only SMB library, Fastify-5-only plugin majors, a stale worker process racing a fresh one for job claims) that a mocked test suite likely wouldn't have. The automated suite added on top keeps that same philosophy rather than replacing it with mocks.

**Vitest, pinned to `3.2.4`, not the current `4.x`.** Vitest 4 makes `vite` a required peer dependency and needs Vite 6/7/8; the dashboard already has a working `vite@5.4.8` from the original scaffold, and forcing a Vite major bump just to get a newer test runner wasn't worth putting that at risk. Vitest 3.2.4's own `vite` dependency range (`^5.0.0 || ^6.0.0 || ^7.0.0-0`) covers the existing 5.4.8 cleanly. One version across every package, each with its own `vitest.config.ts` — matches the existing per-package `tsconfig.json` convention rather than a single root workspace config.

**Real Postgres for backend tests, not a mocked Prisma client.** A dedicated `logikos_dsp_test` database in the same Postgres container (no new docker service). `packages/backend/vitest.config.ts`'s `globalSetup` runs `prisma migrate deploy` against it before the suite (non-interactive, idempotent, safe on every run); `packages/backend/test/setup.ts` truncates the relevant tables in a `beforeEach`. Because every test file shares that one database, `fileParallelism: false` is set deliberately — running files in parallel would let one file's truncate wipe another file's in-flight data.

**CI (`.github/workflows/ci.yml`) runs exactly what a fresh clone needs, and nothing it doesn't.** Two jobs: TypeScript (`pnpm install --frozen-lockfile` → explicit `prisma generate` → `pnpm build` → `pnpm test` against a `postgres:16-alpine` service, the same image as `docker-compose.yml`) and the Go agent (`gofmt` check, `go vet`, `go test`). The steps were first run by hand in a fresh `git clone`, not the working checkout, so nothing gitignored could be silently papering over a missing step — which is how two of them were found to be necessary: the backend test script loads `.env.test` via `--env-file` and dies without it (CI copies the example, whose values are test-only placeholders pointing at exactly that service), and the backend's `tsc` needs the generated Prisma client. `pnpm build` is the lint step: there is still no ESLint, and adding one would mean a wave of unrelated fixes rather than a CI change. The service's database is created as `logikos_dsp_test` directly, so the one-time `CREATE DATABASE` from local setup isn't needed. Dashboard has no suite, so CI builds it but can't test it.

**`packages/backend/src/index.ts` split into `app.ts` (builds and returns the Fastify instance) + `index.ts` (calls `buildApp()` then `.listen()`).** Standard Fastify testing pattern: tests import `buildApp()` and drive it with `app.inject({method, url, ...})` — no real port, but the exact same route/plugin registration code that runs in production.

**Pure logic extracted out of I/O-heavy functions specifically to make it fast-testable.** `packages/classification/src/ner.ts`'s `mapEntitiesToMatches` (confidence filtering, entity-type mapping, redaction) is split out from `findNamedEntities`, which also does real 100MB-model inference — tests exercise the mapping with fixture data in milliseconds, without loading the model. `packages/agent/src/diff.ts`'s `diffSnapshots` (the create/modified/deleted comparison that's the core of the SMB connector's change detection) and `packages/agent/src/quarantinePath.ts`'s `computeQuarantinePath` are both split out entirely into their own files with zero imports from `config.ts` — `config.ts` validates env vars as an import-time side effect (calls `process.exit(1)` if `WATCH_PATH` is unset), so anything that transitively imports it can't be unit tested without faking an agent environment.

**Scope: high-value coverage, not exhaustive.** Covered: `patterns.ts` (regex/Luhn), `mapEntitiesToMatches`, `diffSnapshots`, `computeQuarantinePath`, `parseChildrenPage` (against Microsoft-documented fixture JSON — see the M365 connector note above), `isLocalWatchedRoot`, `contentSampling.ts`'s `isSampleable`, `checkRansomwareRate` (real DB), the response-action approve/agent-commands flow (real DB), and auth/RBAC end to end via `app.inject()` (login, `/auth/me`, 401/403 enforcement — the most security-critical code in the project). **Not yet covered, deliberately** — the same way every other v1 boundary in this project has been documented rather than silently skipped: dashboard components, the chokidar-based `watcher.ts`, the actual file-move I/O in `quarantine.ts` (only its pure path logic is tested), the M365 connector's real network calls (no live tenant available — see above), and live NER model inference (only its pure mapping logic is tested, not the actual ONNX pipeline).

## Production packaging

**Four Dockerfiles, one per service, not a single combined image.** Each package already has its own `build`/`start` scripts and independent lifecycle (the agent restarts on its own schedule regardless of whether classification is mid-model-load); one image per service keeps that independence in production instead of collapsing it behind a process supervisor inside a monolithic container. All four follow the same shape: a `node:24-bookworm-slim` (not `-alpine`) build stage that installs the whole workspace, builds `shared` first (every service but the dashboard depends on it), then `pnpm --filter <pkg> --prod deploy /app` to produce a minimal production `node_modules` (deploy dependencies only, no devDependencies/other-package cruft) — then a slim runtime stage that copies just that `/app` output. Not Alpine: `@prisma/client`'s and `onnxruntime-node`'s prebuilt native binaries target glibc, not Alpine's musl, and matching the base image everywhere is one less thing to reason about differently per service.

**`pnpm install --frozen-lockfile` at the workspace root, in every one of the four Dockerfiles, installs all six packages' dependencies regardless of which service is being built** — there's no per-package pruned install, so the classification image pays for `@prisma/client`'s postinstall and the agent image pays for `onnxruntime-node`'s ~150MB native-binary download even though neither uses them. This is a real inefficiency (each image's install step takes 1-3 minutes), accepted rather than fixed for v1: a filtered/pruned lockfile install is real added complexity (pnpm's `--filter` doesn't prune the lockfile itself, this needs either `pnpm deploy`'s own install step *before* copying source, restructured COPY layers, or a tool like `turbo prune`), and build time isn't yet a problem worth solving — these are infrequent CI/release builds, not an inner dev loop. Compounding this: every Dockerfile does `COPY . .` before `RUN pnpm install`, the simplest correct option (`COPY package.json pnpm-lock.yaml` alone won't work — this is a workspace, so a full install needs every package's own `package.json` too) but the one with the worst cache behavior — Docker's layer cache keys on the exact content hash of `COPY`'s output, so editing *any* file anywhere in the repo (this very document included) invalidates the install layer for *every* service's image, not just the one that changed. Observed directly while writing this section: editing Dockerfiles and docs between builds forced a full multi-minute reinstall each time, for every image, even when no `package.json` had changed.

**Discovered building the backend image: a workspace-root `pnpm install` silently leaves `@prisma/client` ungenerated.** Its postinstall script looks for `prisma/schema.prisma` relative to a working directory that only resolves correctly when pnpm installs are scoped to the backend package itself — installing all six workspace packages at once, it can't find the schema, prints a warning, and moves on rather than failing. Every Prisma-typed query then silently becomes `any`, which doesn't fail until `tsc` throws confusing `implicitly has an 'any' type` errors on unrelated-looking lines. Fixed by running `pnpm --filter @logikos-dsp/backend exec prisma generate` explicitly, after install and before build, in `packages/backend/Dockerfile`.

**Also discovered: Prisma's engine downloader can't detect OpenSSL's version on `node:24-bookworm-slim`**, and defaults to guessing `openssl-1.1.x` — silently wrong, since bookworm ships OpenSSL 3.x. This doesn't fail the build; it fails the query engine at container *runtime*, which is a much worse place to find out. Fixed by installing the `openssl` package via `apt-get` in both the backend image's build and runtime stages, so Prisma can actually detect the real version and fetch the matching engine binary.

**A third Prisma issue, only visible once the backend container actually ran: `pnpm --prod deploy /app` produces a client with the generated code missing again, even after the fix above.** `prisma generate` doesn't ship pre-baked into the `@prisma/client` package — it's code written into one specific already-installed instance's `node_modules` after the fact. `pnpm deploy` builds `/app` as its own independent `node_modules` tree (a fresh install, not a copy of `/repo`'s), so the generate that ran earlier in the build (needed so `tsc` type-checks) never reaches it — the container started, connected to Postgres, ran migrations, and then crashed on the very first import: `SyntaxError: The requested module '@prisma/client' does not provide an export named 'PrismaClient'`. Only surfaced by actually starting the container and reading its logs — a `docker build` succeeding proves nothing about this failure mode, since `tsc` is satisfied by the *first* generate and never touches `/app`. Fixed by generating a second time, after deploy, directly against the deployed tree: `/app/node_modules/.bin/prisma generate --schema /app/prisma/schema.prisma`.

**The NER model's ~100MB of weights are deliberately kept out of the classification image, downloaded on first container start instead.** `packages/classification/.cache/` is already excluded from the Docker build context (`.dockerignore`'s `**/.cache`, same rule that keeps every service's dev caches out of every build) and left that way rather than adding an exception to bake the model in — a named volume (`classification_cache` in `docker-compose.yml`, mounted at `/app/.cache`) persists it across container restarts instead, so the download happens once per deployment, not once per image build. Same tradeoff and same ~20-30s first-start cost this project already accepted for local dev (see README).

**The dashboard is a static build served by `nginx:1.27-alpine`, and its backend URL is fixed at image-build time, not container-start time.** Vite inlines `import.meta.env.VITE_BACKEND_URL` into the JS bundle when it builds — there's no server process at runtime to read a fresh environment variable from, only nginx serving static files. `packages/dashboard/Dockerfile` takes it as a build `ARG` (`docker-compose.yml`'s `DASHBOARD_BACKEND_URL`, defaulting to `http://localhost:4000`) rather than adding a runtime-env-injection mechanism (a common workaround: generate a small `env.js` config file from real environment variables at container startup, loaded before the app bundle) — not built because this deployment doesn't need more than one backend URL per image yet, and it would be the first piece of "config templating" infrastructure in the whole project. **This value must be reachable from the browser**, not from inside the Docker network — `http://backend:4000` resolves between containers on the compose network but means nothing to a browser running outside it, a real trap given every *other* cross-service URL in this compose file (agent → backend, classification → postgres) correctly uses the compose service name.

**`docker-compose.yml` grew from "start Postgres for local dev" into "run the whole product," in the same file, not a separate one.** `pnpm db:up` (`docker compose up -d postgres`) targets one named service and is unaffected by the four services added alongside it; `docker compose up` with no service name now brings up the full stack. A parallel `docker-compose.prod.yml` was the alternative, rejected as the kind of two-files-to-keep-in-sync complexity this project has avoided elsewhere (see the `Source`-interface and single-migration-path decisions above) — one file, where dev workflows already address services individually by name, covers both cases without new mechanism.

**Three small `package.json` changes, made specifically for `pnpm --prod deploy` to work, that look unrelated to Docker at a glance.** `packages/shared`'s `main`/`types` now point at `./dist/index.js`/`./dist/index.d.ts` instead of `./src/index.ts` — dev could get away with pointing straight at TypeScript source (`tsx`/Vite compile on the fly), but a deployed package has no such thing at runtime, only whatever `dist/` contains. Each deployed package's `files` field (`dist`, plus `prisma` for the backend) makes `pnpm deploy`'s output match what the `build`/`--prod deploy` steps actually produce, instead of `pnpm deploy`'s default of guessing from `.gitignore`-like heuristics. And `prisma` (the CLI, not `@prisma/client`) moved from the backend's `devDependencies` to `dependencies` — the runtime image's entrypoint runs `prisma migrate deploy` on every start (see below), and `--prod deploy` strips devDependencies entirely, so the CLI wouldn't exist in `/app` otherwise.

**No native low-footprint agent yet, so "production packaging" packages the same Node/chokidar agent dev already uses.** This section is about deployability, not about closing the Go/Rust agent gap noted in "Design decisions" above — that's still open.

## Deployment behind a shared reverse proxy

**Served at `https://dsp.logikos.dev` through the shared `logikos-gateway` nginx, not a per-project nginx.** That gateway already terminates TLS for `*.logikos.dev` for three other projects on the same host and is the only thing bound to :80/:443; standing up a second TLS terminator would have collided with it. The vhost lives in this repo at `deploy/dsp.conf` and is *copied* into `logikos-gateway/conf.d/` — the gateway's `conf.d` is mounted read-only and the gateway is not a git repo, so without the copy in here the deployment config would be tracked nowhere. Same pattern `logikos-school` uses.

**The dashboard's API base is `https://dsp.logikos.dev/api`, and nginx strips the `/api` prefix** (`proxy_pass http://host.docker.internal:4000/` — the trailing slash does the stripping). The backend serves its routes at the root (`/auth/login`, `/alerts`, ...) and has no `/api` prefix of its own, so the alternative was a second hostname for the API. One hostname was chosen deliberately: it makes the SPA and the API same-origin, which is what lets the httpOnly `SameSite=Lax` session cookie work with no CORS exemption and no `SameSite=None`. The tradeoff is that `VITE_BACKEND_URL` is baked into the bundle at image build time, so **changing the hostname means rebuilding the dashboard image** — the deployment's `DASHBOARD_BACKEND_URL` therefore lives in a gitignored root `.env` rather than being passed ad hoc, so a later `docker compose up --build` can't silently revert it to `http://localhost:4000`.

**The agent-facing endpoints are blocked at the gateway, not in the app.** `/ingest/*`, `/agent-commands*` and `POST /agents/register` authenticate machines by `Agent.key` — and `register` takes no credential at all, by design (see Auth/RBAC). Reachable from the internet that becomes "anyone can register an agent and inject fabricated file events and alerts," which would also drive fabricated `RANSOMWARE_RATE` alerts. The containerised agent reaches the backend over the compose network (`BACKEND_URL=http://backend:4000`) and never transits nginx, so closing them at the edge costs nothing today. This is an edge-level mitigation and deliberately *not* a claim that the endpoints are now authenticated — running an agent on a remote host means removing those blocks and putting real authentication in front of them first. `GET /agents` is a dashboard route and stays open.

**`NODE_ENV=production` is set for the deployed backend specifically because the session cookie's `secure` flag is derived from it** (`routes/auth.ts`). Without it the cookie is issued without `Secure` even though the site is HTTPS-only.

**Postgres is published on `127.0.0.1:5432`, not `0.0.0.0`.** Nothing outside the host needs it — the backend and the classification worker reach it over the compose network, and the host publish exists only for local dev (`pnpm db:up`, `prisma migrate`, `psql`), all of which work unchanged on loopback. Published on all interfaces it was reachable from the whole LAN with the default `logikos/logikos` credentials. Worth knowing for any port added later: Docker writes its own iptables rules for published ports and **bypasses ufw**, so a host firewall policy is not what's protecting these.

**Backend and dashboard publish on `PUBLISH_ADDR` (this install: `172.17.0.1`), because the gateway's blocks were bypassable.** They had been published on `0.0.0.0`, so from the LAN `POST :4000/agents/register` reached the backend directly while the same request through the gateway got 403 — the edge mitigation above only held for traffic that chose to use the edge, and `trustProxy` would believe whatever `X-Forwarded-For` such a client sent. `127.0.0.1` isn't an option: the gateway reaches apps via `host.docker.internal`, which resolves to the docker0 bridge address, not loopback. Binding to that bridge address keeps the gateway path working and closes the LAN one. It's a variable with a `0.0.0.0` default rather than a hardcoded address because docker0's subnet is a property of the host, not of this repo.

**Dev and prod on one host are separated by config (`BACKEND_ENV_FILE`, a `logikos_dsp_dev` database, dev on :4001), not by a second Postgres container.** The deployed backend used to load `packages/backend/.env` — the same file `pnpm dev:backend` reads — so dev ran with production's `JWT_SECRET` (a token signed by a dev backend verified against prod) and with `NODE_ENV=production`, whose `Secure` cookie flag breaks login over `http://localhost`. And that file's `DATABASE_URL` pointed at the production database, where `prisma migrate dev` can offer to reset on drift. A separate database in the existing container follows the `logikos_dsp_test` precedent; a second container would have needed another host port for no isolation that matters on a single-operator host. `BACKEND_ENV_FILE` defaults to the old path so a fresh install keeps the one-file Quickstart.

**The agent container pins `hostname: dsp-agent`.** `Agent.key` is `agent-<sha256(hostname:local:watchPath)[:24]>` — the formula that lets the Go and TypeScript agents register as the same row. In a container the default hostname is the random container ID, so *every* `docker compose up` that recreated the agent minted a brand-new `Agent` row and orphaned the previous one's event history. Pinning the hostname makes the identity stable across redeploys; it also means the derived key is now reproducible from the compose file alone.

**The backend runs with `trustProxy: true`, added when it went behind the gateway.** Fastify otherwise reports every request as originating from the proxy — in this deployment the Docker bridge address — so the request log, which is the only record of who approved a response action or created a user, showed one identical IP for every client on the internet. It is safe specifically because the only route to this process is through nginx; exposing the backend port directly would let a client forge `X-Forwarded-For` and put an arbitrary address in the audit trail.

**`deploy/webhook-logger.mjs` is a local sink for `RESPONSE_WEBHOOK_URL`.** `WEBHOOK_NOTIFICATION` executes synchronously on approve and records the HTTP result, so with nothing listening every approval lands in `FAILED` and half the response-action feature can't be exercised at all. The logger accepts the POST, pretty-prints the payload and returns 200 — enough to make the approve→`EXECUTED` path real and to document the payload shape for wiring up a real Slack/Telegram endpoint. It is a deployment aid, not a product component, so it sits behind a compose profile (`--profile webhook-logger`): it ran by default until Telegram notifications existed, and was then removed from this install, where a plain `docker compose up` would otherwise keep recreating a container nothing uses.

**Backups are a logical `pg_dump`, on a schedule, with a restore path that is actually exercised.** Postgres is the only stateful component that matters — the classification model cache re-downloads and the images rebuild — so a single nightly `-Fc` dump covers it. Custom format over plain SQL because it is compressed and `pg_restore` can do partial and parallel restores. The dump runs *inside* the postgres container because `pg_dump` refuses to dump from a server newer than itself and the image is the only guaranteed source of a matching client.

Two details exist because of how backup stories usually fail. The dump is written to a `.partial` name and renamed only after `pg_restore --list` has read it back, so a truncated file can never be pruned-to as if it were good. And `deploy/restore.sh verify` restores into a throwaway database and diffs its row counts against the live one, so "we have backups" stays a testable claim rather than an assumption — verified here against a real dump: 9 tables, 9 enum types, 17 indexes and a byte-identical password hash.

~~Not solved: the dumps live on the same disk as the database.~~ Solved by off-box backups, below; the backup container replaces `deploy/backup.sh`'s cron entry (kept on the deployed host only until the dashboard schedule is configured there), which writes the same dump files to the same directory, so `restore.sh` is unchanged.

## Off-box backups

**Configured in the dashboard (Administration → Backups), executed by a dedicated `backup` container.** The backend can't run backups itself: the host-side `backup.sh` needed `docker exec`, giving the backend the Docker socket would give it root on the host, and its Debian image has no Postgres 16 client (`pg_dump` refuses to dump a newer server). The worker is built on `postgres:16-alpine` — the one image guaranteed to carry the matching `pg_dump` — plus Alpine's `nodejs`, `rclone` and `age`; its only npm dependency (`pg`) is pure JS, so a `node_modules` built on Debian runs on musl unchanged. Same shape as file servers: settings and a job queue (`BackupSettings`, `BackupRun`) in Postgres, the backend only validates and enqueues, the worker polls, heartbeats, and records outcomes. Restore is deliberately *not* a dashboard button — it stops the services the page runs on — and stays `deploy/restore.sh` plus the instructions shipped inside each bundle.

**One tool behind all three destinations.** S3-compatible (Cloudflare R2, Backblaze B2, AWS, Wasabi, MinIO), SFTP and Google Drive are each just an rclone remote, generated per run by `rcloneConfig.ts` (pure, tested) into a mode-0700 temp dir and deleted afterwards; secrets never appear on a command line. `no_check_bucket` is always set because scoped keys (R2 object tokens, B2 application keys) usually can't create buckets. SFTP paths may be absolute; S3/Drive paths are always relative. Values are refused if they contain a line break, which would otherwise inject extra keys into the INI config.

**Encrypted to an age public key; the private key never touches the server.** The alternative, a passphrase stored server-side, means whoever compromises the server holds both the backups and the means to read them. With a recipient key the server can *write* backups it can never *read*. The consequence the UI states in bold: lose the private key file and no off-box backup can be restored. It's also why the weekly restore check can't test-decrypt the remote bundle — it restores the local dump into a scratch database and checks the remote bundle exists at its uploaded size instead.

**One bundle is enough to rebuild.** Each upload is `logikos-dsp-<UTC stamp>.tar.age` containing the dump, `backend.env` (JWT secret, enroll token, and `SOURCE_CREDENTIALS_KEY`, without which the file-server and destination passwords inside the dump are unreadable), the root `.env`, a manifest with SHA-256 per file, and `RESTORE.txt`. Verified end to end by downloading a bundle from the destination, confirming a wrong age key is refused, decrypting with the right one, checking every checksum, and restoring the dump into a fresh database with matching contents. The local copy stays a plain `.dump` in the same directory and naming `restore.sh` already reads.

**Scheduling that can't double-run or surprise.** A daily UTC time plus an optional weekly restore check an hour later. Slot maths is pure and shared with the backend (`shared/backups.ts`). A slot only counts if it's after the schedule was (re)activated, so enabling at noon doesn't immediately fire "this morning's" backup; after downtime only the latest missed slot runs, once; and `(kind, scheduledFor)` is unique, so a restart or a second worker can't run the same slot twice. Runs are claimed with `FOR UPDATE SKIP LOCKED`; a run left `RUNNING` by a dead worker is failed on next start. The worker heartbeats during long runs so the page doesn't call it offline mid-upload.

**Failures become alerts; errors are rewritten to be actionable.** A failed backup or restore check raises a HIGH `BACKUP_FAILED` alert with a suggested notification, so it reaches Telegram through the same approve-first path as everything else (a destination test doesn't — the admin who clicked is watching). rclone logs every retry with request ids and Drive embeds the full request URL, so raw stderr was unreadable in the dashboard and in Telegram; `describeRcloneError` (tested against real output captured during testing) produces e.g. "access denied — check the access key, secret and that the key can write to this bucket (…)" or "the server's host key doesn't match the pinned one — possible interception…". A failed upload says the local dump was still written.

**Things testing found.** (1) Pinning only the server's ed25519 host key failed with "key mismatch" against a server whose preferred key is RSA: known_hosts treats "known host, different key type" as a mismatch. The generated config now restricts `host_key_algorithms` to the types actually pinned. (2) OpenSSH's `PerSourcePenalties` turns repeated failed test logins into connection resets, which look like a network problem — worth knowing when an admin retries a wrong password several times. (3) A service account can't write to a personal My Drive (no storage quota), so the form requires a Shared drive id for that mode and offers OAuth-token mode (`rclone authorize "drive"`) for personal accounts.

**Not verified:** Google Drive end to end — there were no Google credentials to test with. The config generation is unit-tested and a run with a deliberately invalid service-account key reached `googleapis.com` and reported the key as invalid, which proves the wiring but not an actual upload. S3 was verified against MinIO and SFTP against a real OpenSSH server (password, key, pinned host keys, wrong key, wrong password); neither against the commercial providers themselves.

## Dashboard-managed file servers

**Configuration lives in the backend; scanning stays in the agent.** Before this, an SMB share was watched by starting an agent with `SOURCE_TYPE=smb` and `SMB_*` env vars — one agent process per share, configured on the agent host. Now ADMINs add file servers and their shares under Administration → File Servers, and an agent polls `GET /agent-sync` (every 10s) for the shares assigned to it, reconciling one snapshot-diff loop per share. The obvious alternative — the backend scanning SMB itself — was rejected: it would put file-server reachability and share credentials in the internet-facing process, which is exactly what the agent/backend split exists to avoid, and it would stop a second agent on another network segment from ever taking over some shares. The agent already had every piece needed (`SmbSource`, `snapshotDiff.ts`); what changed is where its list of sources comes from.

**`Source` became the unit that events hang off, not `Agent`.** One agent watching many shares breaks the assumption that an agent has one watched root: the ransomware-rate rule counted per agent (one busy share would have hidden, or manufactured, a burst on another), `supportsQuarantine` read `Agent.watchedRoot`, and the dashboard labelled everything by hostname. `FileEvent`/`StorageSnapshot` now carry a required `sourceId` and `Alert` an optional one; the rule and the quarantine check work per source. `agentId` stays on those rows, meaning "which agent reported it" — still what quarantine commands and agent auth key on. An agent's own env-configured root is also a `Source` (the one with no `fileServerId`), created or relabelled at every registration, so there is one model rather than a special case. The migration creates that default source for each existing agent and backfills every existing row before setting `NOT NULL`; it was run against a restored production dump before being trusted.

**Ingest stays backward compatible.** `sourceId` is optional on the wire: omitted means the agent's default source, which is what the Go agent and any older TypeScript build send. A `sourceId` is accepted only if that source is currently assigned to the authenticated agent, and a batch may carry only one. Agents advertise `capabilities: ["managed-sources"]` at registration; shares can only be assigned to an agent that did, so the dashboard can't silently give a share to the Go agent, which would never scan it.

**Share passwords are encrypted at rest and write-only.** AES-256-GCM (`crypto/credentials.ts`), key from `SOURCE_CREDENTIALS_KEY` in the backend's env, never in the database — a dump alone doesn't reveal share passwords. The API never returns them (the dashboard shows a blank "leave blank to keep" field), audit entries record `passwordReplaced: true` rather than any value, and the only place they're decrypted is `/agent-sync`, for the agent the share is assigned to. The consequence to plan for: **the key has to be backed up separately from the dumps**, or a restored database has credentials nobody can decrypt. Transport between agent and backend is the compose network today; an agent on another host would need TLS in front of `/agent-sync` before this is acceptable.

**Change detection on the agent keeps baselines where it can.** `sourceReconcile.ts` (pure, tested) splits changes into restart (anything about *how to connect*: host, account, password, share, subfolder — the baseline is discarded, so the first scan afterwards seeds rather than reports, and changes made in that gap aren't reported) and re-time (interval only — the loop keeps its baseline). Scans are a `setTimeout` chain, not `setInterval`, so a walk longer than its interval never overlaps itself; a limiter caps concurrent walks (`MAX_CONCURRENT_SCANS`, default 2); every SMB operation has a 60s timeout so a server that disappears mid-walk can't hold a slot forever. After each scan the agent reports `lastScanAt`/file count/size or a translated error (`STATUS_LOGON_FAILURE` → "logon failed — check username, password and domain") — that's the dashboard's status column.

**"Test connection" goes through the agent**, because the backend can't reach file servers by design: the dashboard creates a `ConnectionTest`, the agent picks it up on its next sync, logs on and lists the share root (no walk), and reports. Tests the agent never picks up are failed after 90s rather than spinning.

**Disable keeps history; Delete removes it, and is confirmed by typing the name.** Disabling a server or share just stops scanning. Deleting removes the source's file events, classification results, snapshots, alerts and their response actions in one transaction — deliberately, since that's what an admin asking to delete a server usually means, and the counts are recorded in the audit log. The `Source → FileServer` FK is `RESTRICT`, not `SET NULL`: nulling it would have silently turned a deleted server's shares into rows indistinguishable from an agent's own source.

**What SMB monitoring honestly is, stated in the UI too:** periodic rescans (changes appear within one interval), no user attribution (a rescan sees *what* changed, not *who* — DataSecurity Plus gets that from Windows Security event logs, which this doesn't read), cost proportional to share size (each scan walks the whole tree), and read-only (no quarantine — see "SMB quarantine"). Verified end to end against a real Samba server: connection tests for good/bad password and a missing share, a share scan, a new file with PII-shaped content becoming a source-attributed HIGH alert with only a notification suggested, disable stopping the loop, a wrong password surfacing as the share's error and clearing when fixed, delete removing its history, and the whole add/test/add-share flow through the dashboard.

## Who changed a file

**SMB scanning can only ever answer "what changed"; the username lives in the file server's own Security log.** A rescan diffs `{size, mtime}` — there is no requester identity in that data, and the SMB client can't read one. DataSecurity Plus gets "who" from Windows auditing, and so does this: Security event **5145** (Detailed File Share) records the user, client IP, share, path and the access rights requested, for every share access. 4663 would also work but needs a SACL on every audited folder; 5145 needs one `auditpol` line and no per-folder setup, which is the difference between an admin trying it in a minute and not trying it.

**Collected remotely over WinRM, not by installing an agent on the file server.** The Windows box already exposes 5985, and the existing agent already holds that server's credentials and network position. A native Windows agent would be better — real time instead of a 30s poll, and it's the same component the USN journal work needs — but it's a deployment on someone's production file server, which this doesn't require. The collector is Python (`packages/agent/winrm/collect.py`, Debian's `python3-winrm`, the library Ansible uses) because WinRM's NTLM handshake with message encryption has no maintained Node client; it is a JSON-in/JSON-out subprocess, and every remote failure comes back as `{error}` rather than a non-zero exit, so a wrong password shows up as the file server's collection error rather than a crashed agent. All parsing and decisions stay in TypeScript, where they're unit-tested against captured 5145 XML.

**Polling asks for a bounded range of `EventRecordID`s, not "the newest N since the bookmark".** The obvious query (`EventRecordID > bookmark`, `-MaxEvents 500`) returns the *newest* 500 on a busy server and silently drops everything older — the bookmark would then jump past events nobody ever read. Instead each poll asks for `bookmark < id <= bookmark + window`, so the result can't be truncated; when that window comes back empty but the log has already moved past it, the bookmark skips the window (`nextBookmark`). Enabling collection starts just behind the newest record rather than at zero, so turning it on doesn't replay a Security log with hundreds of thousands of events.

**A rename is logged against the *old* name.** Windows implements a rename as a DELETE right requested on the source name and usually logs nothing against the new one, so matching a `RENAMED` event by its new path found nothing — the first live rename produced a correctly paired rename row with no user beside it. `matchActivity` now accepts a delete (or a write) on `previousPath` as the explanation for a rename, and the backend's lookups search under both names. A delete recorded against some other file still can't explain a plain delete of this one.

**Matching is by path and time, in both directions, and deliberately conservative.** Scans and audit records arrive independently: the scan can notice a change before the poll fetches the record behind it, or after. So the actor is looked up when file events are ingested *and* backfilled when activity is ingested (`backend/src/activity.ts`), touching only events that have no actor yet. The window reaches back one scan interval plus slack and only 30s forward, because a scan reports a change *after* it happened. Reads never match a change — opening a file doesn't modify it — and a write never matches a delete. When several people wrote in the same window the most recent writer before the scan is chosen; with interval-based scanning that's the honest answer, and the full record set stays in `FileActivity` either way. Machine accounts (`HOST$`) are dropped as noise, and reads are dropped in the agent so they never reach the database — on a busy share they are most of the event volume.

**NTLM needs MD4, which OpenSSL 3 hides.** The first live attempt against a real Windows server failed with `ValueError: unsupported hash type md4`: Python's hashlib refuses it, so every WinRM login fails before it starts. The agent image now ships an OpenSSL config that activates the legacy provider, passed to the collector subprocess only — the same problem the SMB client solves for Node with `--openssl-legacy-provider`. Every failure seen against that server is translated into what to do about it (`describeActivityError`): wrong password, WinRM unreachable, an account that connects but can't read the Security log, and this one.

**Least privilege moved the goalposts twice.** Switching the share from an administrator to a read-only service account broke collection in two ways nothing local could have predicted. First, WinRM answered 401: an account that isn't in `Remote Management Users` can't use WinRM at all, which is indistinguishable from a wrong password. Then, with the group added, the plain WinRM shell (what `pywinrm`'s `run_command` drives) returned Access Denied — running commands that way needs Execute on the service's SDDL, which only administrators have by default. PowerShell Remoting's endpoint *does* accept `Remote Management Users`, so the collector now speaks PSRP (`pypsrp`, pinned; Debian doesn't package it) instead of the WinRM shell. That also removed `[Console]::OutputEncoding`, which has no console to set under PSRP. Then reading still failed with "Attempted to perform an unauthorized operation" — while the Security channel's ACL already granted Event Log Readers, which is what made it look like a server misconfiguration. The cause was the query itself: `Get-WinEvent` asks the log for its *metadata* before reading events, and that step needs "Manage auditing and security log", a privilege Event Log Readers doesn't carry. `wevtutil qe` reads the events directly and works with just the group, so the collector uses it. Three protocol/permission layers, each of which only failed once a real service account was used — none of them reproducible without a Windows box. A fourth followed: `wevtutil` wraps each event's XML over several lines, so emitting a separator per output line handed the parser fragments, and every event was silently dropped while the poll itself kept reporting success. The output is joined into one blob and split on `</Event>` instead. That failure mode — healthy status, no data — is the argument for the file server card showing "last read" rather than just the absence of an error.

**Two more live-only failures, both in the client path.** `pywinrm`'s `Session.run_ps` pipes stderr through a helper that calls `str.startswith` on bytes and raises `TypeError` on Python 3 the moment PowerShell writes *anything* to stderr — which it does on the first call ("Preparing modules for first use", as CLIXML progress records). The collector drives `winrm.Protocol` directly instead — open shell, run an encoded command, read output, clean up — which also lets it set codepage 65001 and pass the script as UTF-16 base64. And success is judged by whether usable output came back, not by an exit code or a quiet stderr: PowerShell can answer correctly while still writing progress noise and a non-zero status.

**Copying out of a share can never be a file event, and no amount of server-side work changes that.** Nothing on the share changes, so there is nothing to detect by scanning; the only record is a read, and Windows logs opening a file and copying it as the same event with no byte counts to separate them. Detecting a copy *as a copy* needs an agent on the workstation doing it — which is how DataSecurity Plus does it, and is out of scope here. What this does instead: reads appear in the File Events timeline as `READ` rows (toggleable, and only where read recording is on), so the direction people actually look for a copy shows something, honestly labelled; and volume is treated as the signal, with the bulk-read threshold now per file server — 50 distinct files in five minutes suits a share people work in all day, five suits one that should rarely be read at all.

**Where a file was copied *to* takes an agent on the receiving machine, and then it is one event.** The server cannot know the destination — it hands over bytes and the client decides what to do with them — so this is not a detection that better server-side logic can reach; DataSecurity Plus puts it in an endpoint agent for the same reason. With the Go agent running on a workstation (`native-agent/README.md`), that machine becomes its own source, and `linkCrossSourceCopies` joins a file appearing there to the same filename being read from a share moments earlier: one `COPIED` event carrying `previousSourceId` and `previousPath`, so the dashboard can show "finance share: HR/payroll.csv ⧉ C:/Users/jdoe/Downloads/payroll.csv" with the person who did it. Matching is on the path *tail*, not the filename: a copied folder keeps its shape, so "IT/report.zip" read from the share arriving at `<watched root>/IT/report.zip` is the strongest signal available. Filename alone is not enough in practice — a share that reuses names across folders (report.zip in HR, IT and the root) makes every bulk copy ambiguous, because copying the tree reads all of them within the same second. Measured on a real 12-file copy before this rule: 0 attributed. Structure disambiguates *which file within a share* was copied and nothing more, so candidates spanning two different sources still resolve to nothing — naming the wrong server is worse than naming none. Copies to machines with no agent remain reads plus the bulk-read alert, which is the honest limit.

**A folder listing is logged exactly like a file read**, and on a share people are browsing it is most of the read volume — 257 listings of one folder against a handful of real file reads, in a live test. There is nothing in the event to tell them apart, so the agent checks each read against the files its last scan actually found (`knownFiles.ts`, published by the scan loop): a read of something that isn't a known file is a folder. Writes and deletes are kept regardless, since a brand-new file legitimately isn't in the last scan yet.

**Two things it doesn't see, both inherent to 5145.** The agent's own access — it lists every folder and reads every file it samples, through the share account — is filtered out by account name, because it's this product looking at the share rather than a person using it, and with read recording on it would otherwise raise a bulk-read alert against ourselves. And access that never goes through the share is invisible: editing files while signed in to the server, in the folder the share points at, produces no 5145 at all, so those changes are detected by scanning but carry no user. Catching those needs object-access auditing (4663) with a SACL on the folder, which is a per-folder setup step rather than one `auditpol` line.

**What this is not.** It's near-real-time (a 30s poll), it depends on the server's audit policy staying on, and it attributes changes to *the account that made the SMB request*. `FileActivity` grows with share activity and has no retention policy yet — the same gap the file events table has.

## Telegram notifications

**Telegram is a first-class channel inside `WEBHOOK_NOTIFICATION`, not a new response action type and not a webhook adapter.** The Bot API's `sendMessage` wants `{chat_id, text}`, not the generic alert JSON, so pointing `RESPONSE_WEBHOOK_URL` at it can't work; the options were a translating proxy service (another container to run for one HTTP call) or sending it from the backend. It's the backend. The action type keeps its name because renaming an enum value that already has rows is a migration for no behavioural gain; "webhook notification" now means "notify every configured channel." Both channels can be set: the action is `EXECUTED` only if every configured one succeeded, and `resultMessage` records each (`telegram responded 200; webhook responded 502`) so a partial failure is visible rather than averaged away. A token without a chat id (or the reverse) is reported as a failure, not silently skipped.

**HTML parse mode, not MarkdownV2**, because alert messages and paths are full of `.`, `-` and `_`, all of which MarkdownV2 requires escaping; HTML needs only `&`, `<`, `>`. `formatTelegramAlert` is pure and tested.

**The bot token never reaches `resultMessage`.** It's part of the request URL, and that field is stored and shown on the dashboard, so network errors are reported as a category ("network error", "timed out") rather than by forwarding the fetch error's text; Telegram's own error `description` (e.g. "chat not found") is safe and is passed through. Both channels are bounded to 10s, since approval waits on them.

**Still approve-first.** A Telegram message goes out when an ADMIN approves the suggested notification, not when the alert is raised. That keeps the loop documented above intact, and it means Telegram tells the *rest* of the team about something an admin has already looked at; paging on alert creation would be a separate, deliberate change to that design.

## Data retention

**Nothing was ever deleted.** File events, classification results, storage snapshots, alerts, and now Windows audit records and login attempts, all accumulated forever — fine at 9MB on one watched folder, not fine once shares are scanned on a schedule. Retention is configured under Administration → Retention and swept hourly by the backend (`retention.ts`, started from `index.ts` rather than `app.ts` so tests driving `app.inject()` never start a timer that deletes their own fixtures).

**Off by default, and the page shows what's stored next to each limit.** An install shouldn't quietly start dropping its own audit trail because nobody visited a settings page, and "keep 30 days" means something different when the table holds a year. Deleting is irreversible, so the page points at Backups first.

**Three rules exist because the obvious version loses things people still need.** Each source keeps its *newest* storage snapshot however old it is — otherwise a share that stopped changing disappears from the Storage view rather than showing its last known size. Only `RESOLVED` alerts expire: an open or acknowledged one is still someone's to-do, whatever its age. And file events take their classification jobs and matches with them, because those hang off the event and the FKs are `RESTRICT` — a half-deleted event would fail the sweep rather than corrupt anything, but it would fail it every hour.

**Deletes run in bounded batches** (5,000 rows, at most 20 batches per table per pass) rather than one statement: the first sweep over a long-neglected database would otherwise hold locks for minutes. Whatever's left is picked up an hour later.

## What's deliberately out of scope for v0

- SMB/M365/Google Drive share quarantine — SMB was actually attempted and reverted after live testing found a hard `v9u-smb2` library limitation, not just deferred; M365/Google Drive stay read-only by design (their OAuth scopes are `.readonly`, deliberately). See "SMB quarantine" above. Local-path quarantine for both `SENSITIVE_DATA_EXPOSED` alerts and `RANSOMWARE_RATE` bursts is covered (see "Automated response"/"Ransomware-burst quarantine" above).
- **Real share-admin response actions ("disable this share," "kill this process")** — deliberately not built, not just unbuilt. This got a design pass, not an implementation, because the two candidate actions don't fail safely the way quarantine does (a quarantine mistake moves one file into a subfolder; a wrong `kill` or a disabled share while people are using it is real, immediate operational damage) and neither has a live environment in this project to verify against the way SMB quarantine did:
  - **"Kill this process"** needs a way to attribute a burst of file events to a specific PID in the first place — the agent doesn't have that today (chokidar/fanotify report *what* changed, not *who* changed it), and getting it means real per-OS work: Windows would need ETW or a minifilter driver reading `IO_STACK_LOCATION`'s requestor info, Linux would need `fanotify`'s `FAN_REPORT_PID` (kernel 5.15+) or `/proc/net`-style handle scanning under a race. Even with correct attribution, killing a process based on a rate heuristic risks killing a legitimate bulk job (a backup, a build, a migration script) — the same false-positive risk `RANSOMWARE_RATE` already has for its existing webhook suggestion, but with an action that can't be undone by moving a file back.
  - **"Disable this share"** needs credentials with real administrative control over the file server (`net share /delete` on Windows, editing and reloading `smb.conf` on Samba) — a fundamentally different, much higher-privilege trust boundary than the read-only (and, per the finding above, not even reliably write-capable) credentials this project's connectors use today. Granting that scope to the same service account that's scanning file content would also undermine the "agent is a client, not an administrator" security posture the M365/Google Drive OAuth scopes were deliberately chosen to preserve (see those connectors' notes above).

  Both would reuse the existing approve-first `ResponseAction` machinery if built (new `type` enum values, same `PENDING`→approve→execute flow) — the missing piece is safe, verifiable *capability* to execute them, not the suggestion/approval plumbing.
- **True NTFS USN journal support** — `native-agent/` (Go) exists now for local-path watching (see "Design decisions" above) but uses `fsnotify`, not the USN journal directly; that's still open, blocked on having a real Windows machine to develop and test it against safely. Linux `fanotify` was also tried instead of `inotify` and found blocked in this specific dev sandbox (`fanotify_init` returns `EPERM` — no `CAP_SYS_ADMIN` available even though the capability bounding set nominally includes it), not a fundamental blocker elsewhere. SMB/M365/Google Drive watching also isn't reimplemented in the native agent — those stay on `packages/agent`.
