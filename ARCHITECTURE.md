# Architecture

## Goal

Replace the core workflows of ManageEngine DataSecurity Plus:

1. **File Audit / FIM** — who touched what file, when, from where.
2. **Data Risk Assessment (DRA)** — where is sensitive data (PII/PCI/PHI-shaped content) sitting, and is it over-exposed.
3. **Ransomware / anomaly detection** — spot mass-encryption/mass-delete behavior fast, raise an alert, and let a human approve a response action.
4. **Disk/storage analysis** — track storage growth and usage per share/path over time.

## Design decisions

**All TypeScript for v0, not Go/Rust for the agent.** DSP's real agent needs to run as a low-footprint Windows service reading the NTFS USN journal, which argues for Go or Rust in production. This dev environment doesn't have a Go toolchain, and the priority right now is proving the end-to-end pipeline (event → rule → alert → dashboard) rather than agent footprint. The agent package is isolated behind a plain HTTP ingest contract specifically so it can be rewritten in Go/Rust later without touching the backend, classification worker, or dashboard — only `packages/agent` changes.

**Postgres only, no Kafka/Elasticsearch yet.** Event volume at pilot scale (a handful of watched paths) fits comfortably in a well-indexed Postgres table partitioned by day. Introducing a stream broker or search cluster before there's a concrete scale/query problem would be premature — revisit if/when: (a) ingest volume needs durable buffering across backend restarts, or (b) full-text/fuzzy search across audit history becomes a product requirement.

**Rules run inline in the backend, not a separate stream processor.** The ransomware/anomaly rule (event-rate-per-agent-per-minute) is cheap enough to evaluate synchronously on ingest. A dedicated stream-processing layer (Flink/ksqlDB-style) is overkill until rules get materially more complex (cross-path correlation, ML-based baselining).

**Classification is a separate worker, not inline on ingest.** Content scanning (reading file bytes, running pattern/format checks) is I/O- and CPU-heavier and shouldn't block the hot ingest path. It polls a `ClassificationJob` queue backed by Postgres (`pg-boss`-style `FOR UPDATE SKIP LOCKED`), which avoids standing up Redis/RabbitMQ for v0 while still being safe for multiple workers.

**Classification runs a regex pass and a local NER pass, not just one or the other.** `packages/classification/src/patterns.ts` (unchanged) catches structured data — SSN, Luhn-checked credit card, email, phone. `packages/classification/src/ner.ts` adds unstructured detection — person names, organizations, locations — via a local named-entity-recognition model (`@huggingface/transformers` running `Xenova/bert-base-NER`, CoNLL entity types PER/ORG/LOC; MISC is dropped as too broad to be a useful signal). **Local was a deliberate choice over calling a cloud LLM API**: a data-security product routing the content it's protecting through a third-party API to classify it would undermine its own purpose, and would be a real compliance problem for actual PII/PHI. "Local" means inference — the part that touches file content — never leaves the machine via ONNX Runtime/WASM. Model *weights* (~100MB, cached under `packages/classification/.cache/`, gitignored) download once from Hugging Face Hub on first run; that's a one-time setup step comparable to `docker pull`, not an ongoing data path, but worth being explicit about so "local model" isn't misread as "no internet, ever." The model loads once at worker startup (`preloadNerModel()`, before the poll loop begins) rather than per job, so a broken load fails loudly at boot instead of silently mid-job, and the first real classification job isn't stuck paying multi-second load latency. Matches below a confidence threshold (0.85) are dropped — BERT NER can misfire on short/lowercase tokens. **Known v1 tradeoff, not yet solved**: NER inference runs sequentially per job like the regex pass, and is meaningfully slower (seconds, not microseconds) — this will visibly reduce worker throughput under load; batching/concurrency is a natural follow-up once that's a real bottleneck rather than a hypothetical one.

**Automated response is a suggest-and-approve loop, not literal automation, and only does what the system can actually do.** Real DSP-style responses ("disable this share," "kill this process") assume the tool operates the file server — logikos-dsp's agent is a client that watches shares, it doesn't administer them, so those aren't implemented. v1 has two response action types: **webhook notification** (`packages/backend/src/responseActions/webhook.ts`, POSTing alert details to `RESPONSE_WEBHOOK_URL`) and **file quarantine** (local-path agents only, see below). Nothing fires automatically regardless of severity: HIGH/CRITICAL alerts get `ResponseAction` row(s) created in `PENDING` status (by `packages/backend/src/rules/ransomwareRate.ts` for CRITICAL ransomware-rate alerts — notification only, there's no single file to quarantine; by the classification worker for HIGH sensitive-data alerts — both notification and quarantine, independently), and nothing executes until an ADMIN calls `POST /response-actions/:id/approve`; `POST /response-actions/:id/reject` dismisses a suggestion as a false positive without executing anything. This is a firm product requirement, not a placeholder to relax later. `ResponseAction` is its own table (not columns bolted onto `Alert`) so the alert lifecycle (open/acknowledged/resolved) and the response lifecycle (pending/approved/rejected/executed/failed) stay separate concerns.

**File quarantine can't execute synchronously in the approve request, unlike webhook notification — only the agent has filesystem access to the watched directory.** Approving a `FILE_QUARANTINE` action sets it to `APPROVED` (a status that exists *only* for this reason — webhook notification skips straight to `EXECUTED`/`FAILED`), not a final state. The local-mode agent polls `GET /agent-commands?agentKey=...` (`packages/agent/src/quarantine.ts`, `packages/backend/src/routes/agentCommands.ts`) — the same "which file, which agent" data already lives on the linked `Alert` (`agentId`, `metadata.path`), so no new columns were needed on `ResponseAction` — moves the file into a `.logikos-quarantine/` subfolder *inside* the watched root (no new permission surface, no new `QUARANTINE_DIR` config), and reports back via `POST /agent-commands/:id/complete`, which is what actually sets `EXECUTED`/`FAILED`. That subfolder is excluded from the chokidar watch (`watcher.ts`'s `ignored` option) so the move itself never produces a spurious `FileEvent`. Both endpoints are agent-facing (`Agent.key`, never `app.authenticate`) — same two-identity-system split as `ingest.ts`. Quarantine is suggested only for `SENSITIVE_DATA_EXPOSED` alerts (exactly one file to act on) and only for local-path agents (`Agent.watchedRoot` not starting with `smb://` — the SMB connector stays read-only); `RANSOMWARE_RATE` alerts, which are about an event-rate burst with no single file, only ever get a notification suggestion.

**The "suggest a response action" step is duplicated in the two places that create alerts, not centralized.** Alerts are created from two different processes with two different DB clients — the backend's ransomware-rate rule (Prisma) and the classification worker (raw `pg`, see below). Rather than force a shared abstraction across that process boundary, or use a Postgres trigger (which would make the suggestion policy invisible from reading either codebase), each call site gets its own small "if severity is HIGH/CRITICAL, also insert a PENDING `ResponseAction`" step, right next to where it creates the `Alert`. Consistent with this project's general preference for explicit over magic (the seed script instead of auto-created admin, explicit env vars throughout) — a few duplicated lines that are easy to find beat one clever mechanism that isn't visible from either call site.

**Storage analysis piggybacks on the agent.** Rather than a separate crawler, the agent periodically walks its watched root and reports aggregate size/file-count snapshots — same transport, same auth, no new component.

**Storage sources are pluggable behind a `Source` interface, each free to use its own detection strategy.** `packages/agent/src/sources/types.ts` defines `Source` (`describe()`, `listTree()`, `readSample()`). Local paths (`packages/agent/src/watcher.ts`) use `chokidar` for real-time OS filesystem events, unchanged since v0. SMB/network shares (`packages/agent/src/sources/smb.ts`) instead use **periodic snapshot diffing** (`packages/agent/src/snapshotDiff.ts`): walk the share on an interval, diff against the previous walk's `{size, mtime}` map, synthesize created/modified/deleted events. This was a deliberate choice over mounting the share locally and reusing chokidar — CIFS/NFS client mounts don't reliably propagate inotify events for remote-side changes, so a "real-time" mount-based watcher can silently miss changes. The tradeoff is detection latency bounded by the scan interval (`SMB_SCAN_INTERVAL_MS`, default 30s) instead of true real-time, and — same limitation chokidar already has for local paths — no reliable rename or permission-change detection (a move shows up as delete+create). One walk serves both FIM events and the storage snapshot for SMB sources, since the tree walk already has full size/count data; local mode still does these separately (chokidar has no "list everything" step to piggyback on).

This required **no backend or dashboard changes** — `Agent.watchedRoot`, `FileEvent.path`, and `StorageSnapshot.rootPath` were already unconstrained strings, so an SMB agent just registers with `watchedRoot: "smb://host/share/sub"` and everything downstream works unchanged. Confirms the v0 bet on isolating the agent behind a plain HTTP contract.

**SMB client: `v9u-smb2`, not the more well-known `@marsaud/smb2` it forks — verified the hard way.** Both are pure-JS SMB2/3 clients (no OS-level `mount -t cifs`, no root/CAP_SYS_ADMIN needed — works from a container), and both self-describe as "experimental." `@marsaud/smb2` was tried first and rejected: it bundles the `ntlm` package, which only ever speaks NTLMv1 (confirmed by reading its source — no HMAC-MD5/NTLMv2 code at all) and reliably failed `STATUS_LOGON_FAILURE` against this project's test Samba container even with NTLMv1 explicitly permitted server-side. `v9u-smb2` swaps that dependency for `ntlm2`, which implements real NTLMv2, and connects successfully. Both libraries still hash the legacy LM response via DES-ECB and the NT hash via MD4 — algorithms OpenSSL 3's default provider disables — so **the agent process requires `NODE_OPTIONS=--openssl-legacy-provider` whenever `SOURCE_TYPE=smb`** (see README). Separately, the shipped `index.d.ts` doesn't resolve cleanly as a default export under this project's `moduleResolution: NodeNext`, and omits `size` from stat results even though the underlying implementation always sets it (verified by reading `lib/tools/stats.js`). `sources/smb.ts` works around both by loading the package via `createRequire` and declaring only the surface it actually uses, checked against the real implementation — rather than fighting the package's types. If `v9u-smb2` itself proves unreliable in practice, the next fallback is shelling out to the `smbclient` CLI, not pursued since NTLMv2 auth is now working.

**Microsoft 365 (OneDrive/SharePoint) connector: same `Source`/snapshot-diff machinery as SMB, zero changes to that shared code.** `packages/agent/src/sources/m365.ts` implements `describe()`/`listTree()`/`readSample()` like `sources/smb.ts` does — the only new code is a third `Source`, everything downstream (diffing, event batching, storage snapshots) is already-proven infrastructure. Auth is the OAuth 2.0 **client credentials grant** (app-only, no user sign-in — an Azure AD app registration with `Files.Read.All`/`Sites.Read.All` **Application** permissions and admin consent, the standard "daemon app" shape), implemented with plain `fetch` rather than `@azure/msal-node` or the Graph SDK — token acquisition is one documented `POST`, not worth a new dependency. One configured `M365_DRIVE_ID` (+ optional `M365_SUBPATH`) per agent, matching the SMB connector's "one configured share" scope — no org-wide auto-discovery of every user's OneDrive or every SharePoint site. Uses Graph's plain paginated `children` listing on a scan interval (`M365_SCAN_INTERVAL_MS`, default 60s — more conservative than SMB's 30s, since this hits a rate-limited cloud API), not Graph's `/delta` incremental-changes API — delta queries would mean new state (delta tokens) and a genuinely different code path, and given this connector can't be tested against a real tenant right now (see below), minimizing new mechanism surface mattered more than the efficiency win.

**This connector has not been verified against a real Microsoft 365 tenant** — unlike every other connector in this project (SMB was checked against a real test Samba container; the local watcher, obviously, against a real filesystem), no Azure AD credentials were available while building it. Every endpoint, request/response shape, and auth flow detail above is grounded in Microsoft's current Graph API documentation (fetched and read directly while designing this, not recalled from training data), and the pure response-parsing logic (`parseChildrenPage` in `sources/m365.ts`) is unit-tested against fixture JSON copied verbatim from Microsoft's own documented example responses — but the actual network calls, real permission/consent behavior, and error responses are unverified. Treat the first real run against a live tenant as the actual verification step, and watch its logs closely.

**The classification worker's "is this agent local (write-capable)" check generalizes from an `smb://`-specific prefix check to "watchedRoot contains no URI scheme."** `packages/classification/src/watchedRoot.ts`'s `isLocalWatchedRoot()` — `!watchedRoot.includes("://")` — decides whether a `HIGH` sensitive-data alert also gets a `FILE_QUARANTINE` suggestion alongside the webhook notification. Both SMB and M365 watchedRoots carry a `scheme://` prefix and are both read-only in v1, so this one check now correctly excludes both (and any future URI-based connector) without an ever-growing prefix allow-list.

## Data flow

```
 watched filesystem
        |
        v
   [agent]  --(FileEvent)-->  POST /ingest/events  --> [backend] --> Postgres (file_event)
        |                                                  |
        |--(StorageSnapshot, periodic)-->  POST /ingest/storage        |-- rate rule --> alert (Postgres)
                                                                        |
                                                        [classification worker] <-- polls classification_job
                                                                        |
                                                                        v
                                                        classification_match (+ alert if sensitive)

                                        [dashboard] <--REST--> [backend]  (events, alerts, storage trends, matches)
```

## Core entities (Prisma schema, `packages/backend/prisma/schema.prisma`)

- `Agent` — a registered watcher (host + watched root).
- `FileEvent` — one filesystem event (create/modify/delete/rename/permission_change) from an agent.
- `StorageSnapshot` — periodic size/file-count rollup for an agent's watched root.
- `ClassificationJob` — queued "scan this file" work item, created on file create/modify events.
- `ClassificationMatch` — a sensitivity-pattern hit (type: SSN/credit-card/email/etc, with a redacted sample) for a file.
- `Alert` — a raised alert (ransomware-rate, sensitive-data-exposed, ...), with severity and status.
- `ResponseAction` — a suggested response to an alert (currently only `WEBHOOK_NOTIFICATION`), pending until an ADMIN approves or rejects it.
- `User` — a dashboard login (`email`, `passwordHash`, `role`). Unrelated to `Agent`, see below.

## Auth/RBAC

**Two identity systems, deliberately kept separate.** `Agent.key` authenticates *machines* (agent processes calling `POST /agents/register`, `POST /ingest/events`, `POST /ingest/storage`) and was never touched by this feature. `User` + a cookie-based JWT authenticates *people* using the dashboard, gating every other endpoint (`/events`, `/alerts`, `/storage`, `/classification-*`, `/agents` GET, `/users`). Mixing these would mean either forcing unattended agent processes to hold a user session (no such user exists) or weakening the dashboard's auth to match agents' simple shared-secret model — neither is right, so the two stay on completely separate code paths. In `packages/backend/src/index.ts`, agent-facing routes are registered with a comment marking them as never-gated; dashboard-facing route files each self-gate via `app.addHook("onRequest", app.authenticate)`.

**Cookie-based JWT, not a session table.** Consistent with the "Postgres only, no extra infra" stance below: a signed JWT in an httpOnly cookie (`@fastify/jwt` + `@fastify/cookie`) needs no session store, while still being safe against XSS token theft (unlike JWT-in-localStorage). No refresh-token flow in v1 — a user just logs in again after the token expires; revisit if session lifetime becomes a real complaint.

**Two roles: `ADMIN` and `VIEWER`.** ADMIN can do everything, including managing users and acknowledging/resolving alerts (`PATCH /alerts/:id` requires it); VIEWER is read-only. A finer-grained role (e.g. can-acknowledge-but-not-manage-users) is a natural v2 addition once there's a real need for it.

**`@fastify/jwt`/`@fastify/cookie` are pinned to their last Fastify-4-compatible majors** (`8.0.1` / `9.4.0`) — their current majors (10.x / 11.x) require Fastify 5, which this project isn't on. Bumping Fastify itself would be the right way to pick up newer versions, not a piecemeal plugin upgrade.

**Bootstrap admin via a seed script, not auto-creation.** `packages/backend/prisma/seed.ts` creates one `ADMIN` from `ADMIN_EMAIL`/`ADMIN_PASSWORD` env vars if no `User` rows exist yet (`pnpm db:seed`) — explicit and scriptable, rather than a magic first-run behavior that's easy to trigger by accident.

## Testing

Every feature up to this point was verified by hand — live processes, curl scripts, real Postgres, a real Samba container, a real webhook listener. That caught real bugs (an NTLMv1-only SMB library, Fastify-5-only plugin majors, a stale worker process racing a fresh one for job claims) that a mocked test suite likely wouldn't have. The automated suite added on top keeps that same philosophy rather than replacing it with mocks.

**Vitest, pinned to `3.2.4`, not the current `4.x`.** Vitest 4 makes `vite` a required peer dependency and needs Vite 6/7/8; the dashboard already has a working `vite@5.4.8` from the original scaffold, and forcing a Vite major bump just to get a newer test runner wasn't worth putting that at risk. Vitest 3.2.4's own `vite` dependency range (`^5.0.0 || ^6.0.0 || ^7.0.0-0`) covers the existing 5.4.8 cleanly. One version across every package, each with its own `vitest.config.ts` — matches the existing per-package `tsconfig.json` convention rather than a single root workspace config.

**Real Postgres for backend tests, not a mocked Prisma client.** A dedicated `logikos_dsp_test` database in the same Postgres container (no new docker service). `packages/backend/vitest.config.ts`'s `globalSetup` runs `prisma migrate deploy` against it before the suite (non-interactive, idempotent, safe on every run); `packages/backend/test/setup.ts` truncates the relevant tables in a `beforeEach`. Because every test file shares that one database, `fileParallelism: false` is set deliberately — running files in parallel would let one file's truncate wipe another file's in-flight data.

**`packages/backend/src/index.ts` split into `app.ts` (builds and returns the Fastify instance) + `index.ts` (calls `buildApp()` then `.listen()`).** Standard Fastify testing pattern: tests import `buildApp()` and drive it with `app.inject({method, url, ...})` — no real port, but the exact same route/plugin registration code that runs in production.

**Pure logic extracted out of I/O-heavy functions specifically to make it fast-testable.** `packages/classification/src/ner.ts`'s `mapEntitiesToMatches` (confidence filtering, entity-type mapping, redaction) is split out from `findNamedEntities`, which also does real 100MB-model inference — tests exercise the mapping with fixture data in milliseconds, without loading the model. `packages/agent/src/diff.ts`'s `diffSnapshots` (the create/modified/deleted comparison that's the core of the SMB connector's change detection) and `packages/agent/src/quarantinePath.ts`'s `computeQuarantinePath` are both split out entirely into their own files with zero imports from `config.ts` — `config.ts` validates env vars as an import-time side effect (calls `process.exit(1)` if `WATCH_PATH` is unset), so anything that transitively imports it can't be unit tested without faking an agent environment.

**Scope: high-value coverage, not exhaustive.** Covered: `patterns.ts` (regex/Luhn), `mapEntitiesToMatches`, `diffSnapshots`, `computeQuarantinePath`, `parseChildrenPage` (against Microsoft-documented fixture JSON — see the M365 connector note above), `isLocalWatchedRoot`, `contentSampling.ts`'s `isSampleable`, `checkRansomwareRate` (real DB), the response-action approve/agent-commands flow (real DB), and auth/RBAC end to end via `app.inject()` (login, `/auth/me`, 401/403 enforcement — the most security-critical code in the project). **Not yet covered, deliberately** — the same way every other v1 boundary in this project has been documented rather than silently skipped: dashboard components, the chokidar-based `watcher.ts`, the actual file-move I/O in `quarantine.ts` (only its pure path logic is tested), the M365 connector's real network calls (no live tenant available — see above), and live NER model inference (only its pure mapping logic is tested, not the actual ONNX pipeline).

## Production packaging

**Four Dockerfiles, one per service, not a single combined image.** Each package already has its own `build`/`start` scripts and independent lifecycle (the agent restarts on its own schedule regardless of whether classification is mid-model-load); one image per service keeps that independence in production instead of collapsing it behind a process supervisor inside a monolithic container. All four follow the same shape: a `node:24-bookworm-slim` (not `-alpine`) build stage that installs the whole workspace, builds `shared` first (every service but the dashboard depends on it), then `pnpm --filter <pkg> --prod deploy /app` to produce a minimal production `node_modules` (deploy dependencies only, no devDependencies/other-package cruft) — then a slim runtime stage that copies just that `/app` output. Not Alpine: `@prisma/client`'s and `onnxruntime-node`'s prebuilt native binaries target glibc, not Alpine's musl, and matching the base image everywhere is one less thing to reason about differently per service.

**`pnpm install --frozen-lockfile` at the workspace root, in every one of the four Dockerfiles, installs all six packages' dependencies regardless of which service is being built** — there's no per-package pruned install, so the classification image pays for `@prisma/client`'s postinstall and the agent image pays for `onnxruntime-node`'s ~150MB native-binary download even though neither uses them. This is a real inefficiency (each image's install step takes 1-3 minutes), accepted rather than fixed for v1: a filtered/pruned lockfile install is real added complexity (pnpm's `--filter` doesn't prune the lockfile itself, this needs either `pnpm deploy`'s own install step *before* copying source, restructured COPY layers, or a tool like `turbo prune`), and build time isn't yet a problem worth solving — these are infrequent CI/release builds, not an inner dev loop. Compounding this: every Dockerfile does `COPY . .` before `RUN pnpm install`, the simplest correct option (`COPY package.json pnpm-lock.yaml` alone won't work — this is a workspace, so a full install needs every package's own `package.json` too) but the one with the worst cache behavior — Docker's layer cache keys on the exact content hash of `COPY`'s output, so editing *any* file anywhere in the repo (this very document included) invalidates the install layer for *every* service's image, not just the one that changed. Observed directly while writing this section: editing Dockerfiles and docs between builds forced a full multi-minute reinstall each time, for every image, even when no `package.json` had changed.

**Discovered building the backend image: a workspace-root `pnpm install` silently leaves `@prisma/client` ungenerated.** Its postinstall script looks for `prisma/schema.prisma` relative to a working directory that only resolves correctly when pnpm installs are scoped to the backend package itself — installing all six workspace packages at once, it can't find the schema, prints a warning, and moves on rather than failing. Every Prisma-typed query then silently becomes `any`, which doesn't fail until `tsc` throws confusing `implicitly has an 'any' type` errors on unrelated-looking lines. Fixed by running `pnpm --filter @logikos-dsp/backend exec prisma generate` explicitly, after install and before build, in `packages/backend/Dockerfile`.

**Also discovered: Prisma's engine downloader can't detect OpenSSL's version on `node:24-bookworm-slim`**, and defaults to guessing `openssl-1.1.x` — silently wrong, since bookworm ships OpenSSL 3.x. This doesn't fail the build; it fails the query engine at container *runtime*, which is a much worse place to find out. Fixed by installing the `openssl` package via `apt-get` in both the backend image's build and runtime stages, so Prisma can actually detect the real version and fetch the matching engine binary.

**A third Prisma issue, only visible once the backend container actually ran: `pnpm --prod deploy /app` produces a client with the generated code missing again, even after the fix above.** `prisma generate` doesn't ship pre-baked into the `@prisma/client` package — it's code written into one specific already-installed instance's `node_modules` after the fact. `pnpm deploy` builds `/app` as its own independent `node_modules` tree (a fresh install, not a copy of `/repo`'s), so the generate that ran earlier in the build (needed so `tsc` type-checks) never reaches it — the container started, connected to Postgres, ran migrations, and then crashed on the very first import: `SyntaxError: The requested module '@prisma/client' does not provide an export named 'PrismaClient'`. Only surfaced by actually starting the container and reading its logs — a `docker build` succeeding proves nothing about this failure mode, since `tsc` is satisfied by the *first* generate and never touches `/app`. Fixed by generating a second time, after deploy, directly against the deployed tree: `/app/node_modules/.bin/prisma generate --schema /app/prisma/schema.prisma`.

**The NER model's ~100MB of weights are deliberately kept out of the classification image, downloaded on first container start instead.** `packages/classification/.cache/` is already excluded from the Docker build context (`.dockerignore`'s `**/.cache`, same rule that keeps every service's dev caches out of every build) and left that way rather than adding an exception to bake the model in — a named volume (`classification_cache` in `docker-compose.yml`, mounted at `/app/.cache`) persists it across container restarts instead, so the download happens once per deployment, not once per image build. Same tradeoff and same ~20-30s first-start cost this project already accepted for local dev (see README).

**The dashboard is a static build served by `nginx:1.27-alpine`, and its backend URL is fixed at image-build time, not container-start time.** Vite inlines `import.meta.env.VITE_BACKEND_URL` into the JS bundle when it builds — there's no server process at runtime to read a fresh environment variable from, only nginx serving static files. `packages/dashboard/Dockerfile` takes it as a build `ARG` (`docker-compose.yml`'s `DASHBOARD_BACKEND_URL`, defaulting to `http://localhost:4000`) rather than adding a runtime-env-injection mechanism (a common workaround: generate a small `env.js` config file from real environment variables at container startup, loaded before the app bundle) — not built because this deployment doesn't need more than one backend URL per image yet, and it would be the first piece of "config templating" infrastructure in the whole project. **This value must be reachable from the browser**, not from inside the Docker network — `http://backend:4000` resolves between containers on the compose network but means nothing to a browser running outside it, a real trap given every *other* cross-service URL in this compose file (agent → backend, classification → postgres) correctly uses the compose service name.

**`docker-compose.yml` grew from "start Postgres for local dev" into "run the whole product," in the same file, not a separate one.** `pnpm db:up` (`docker compose up -d postgres`) targets one named service and is unaffected by the four services added alongside it; `docker compose up` with no service name now brings up the full stack. A parallel `docker-compose.prod.yml` was the alternative, rejected as the kind of two-files-to-keep-in-sync complexity this project has avoided elsewhere (see the `Source`-interface and single-migration-path decisions above) — one file, where dev workflows already address services individually by name, covers both cases without new mechanism.

**Three small `package.json` changes, made specifically for `pnpm --prod deploy` to work, that look unrelated to Docker at a glance.** `packages/shared`'s `main`/`types` now point at `./dist/index.js`/`./dist/index.d.ts` instead of `./src/index.ts` — dev could get away with pointing straight at TypeScript source (`tsx`/Vite compile on the fly), but a deployed package has no such thing at runtime, only whatever `dist/` contains. Each deployed package's `files` field (`dist`, plus `prisma` for the backend) makes `pnpm deploy`'s output match what the `build`/`--prod deploy` steps actually produce, instead of `pnpm deploy`'s default of guessing from `.gitignore`-like heuristics. And `prisma` (the CLI, not `@prisma/client`) moved from the backend's `devDependencies` to `dependencies` — the runtime image's entrypoint runs `prisma migrate deploy` on every start (see below), and `--prod deploy` strips devDependencies entirely, so the CLI wouldn't exist in `/app` otherwise.

**No native low-footprint agent yet, so "production packaging" packages the same Node/chokidar agent dev already uses.** This section is about deployability, not about closing the Go/Rust agent gap noted in "Design decisions" above — that's still open.

## What's deliberately out of scope for v0

- Google Drive/Workspace connector — Microsoft 365 was built first (see above); a Google connector would follow the same `Source`-implementation pattern.
- SMB/M365 share quarantine (both stay read-only by design), and quarantining files touched during a `RANSOMWARE_RATE` burst (no single file to act on) — all need their own design pass. Local-path file quarantine for `SENSITIVE_DATA_EXPOSED` alerts is covered (see "Automated response" above).
